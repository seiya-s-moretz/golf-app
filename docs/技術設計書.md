## 1. システム概要（既存踏襲）

本アプリは、ゴルフプレイヤー同士のマッチング、ラウンド募集、掲示板投稿、プロフィール管理を行うコミュニティサービスである。目的は、ゴルフ仲間の発見、ラウンド参加の促進、コミュニティ形成である（既存設計書 1章を継承、変更なし）。

PRDにより、以下がMVPスコープに追加された。
- ラウンド参加承認後・マッチング申請承認後の当事者間メッセージ
- 通報・ブロックによる安全機能
- 登録時のSMS等による簡易本人確認
- 将来のエリア拡大に耐えるエリアマスタ管理

対象OS: MVPはAndroidのみ（PRD 5章に準拠、既存設計に変更なし）。

## 2. アーキテクチャ方針（既存踏襲）

- **MVVM + Container + Hilt + Clean Architecture**（既存設計書 3章を継承）
- UI とロジックを完全分離。ViewModel は UiState（不変データクラス）を `StateFlow` で公開し、Container が Screen に橋渡しする
- 依存注入は Hilt を使用
- レイヤー責務（既存踏襲）
  - `ui/` : 画面表示・ユーザー操作の受付のみ。ビジネスロジックを持たない
  - `domain/` : ビジネスモデル・リポジトリインターフェース・ユースケース（フレームワーク非依存）
  - `data/` : API通信、DTO、DTO⇔Domainモデルのマッピング、リポジトリ実装
  - `di/` : Hiltモジュール

**拡張方針**: 新機能（メッセージ／通報・ブロック／本人確認／エリアマスタ）もこのレイヤー構成・命名規則を踏襲する。新規に導入するモジュール（認証層）についても同じ4層構成に従う。

既存設計にはAPI認証・セッション管理の定義が存在しない（`ApiService.kt` にトークンの概念がない）。本人確認機能の追加に伴い、最低限の認証基盤を新設する必要がある。詳細は ADR-0003 を参照。

サーバーサイドの実行環境は TypeScript(Node.js) + Cloud Functions for Firebase、DBは Firestore を採用する（**確定**。プロダクトオーナー確認、10章#6参照）。本書はモバイルアプリ側のアーキテクチャ・API仕様（インターフェース契約）を主眼とし、サーバー実装の詳細設計（関数分割、Firestoreのコレクション設計・インデックス設計等）はDeveloperAgent着手時に別途行う。

### 3-3. メッセージ機能のナビゲーション位置（確定）

メッセージ一覧画面はフッターメニュー5番目のタブとして追加する（5タブ化）。プロダクトオーナー確認により、暫定推奨案のまま正式採用が確定した（未読件数のバッジ表示など、メッセージ機能の可視性を担保するため）。既存4タブ（ホーム／おすすめユーザー／掲示板／マイページ）はそのままの並びを維持し、5番目に「メッセージ」タブを追加する。API・データモデル・画面遷移はもともと両パターンに対応可能な形で設計していたため、本決定に伴う設計変更は発生しない。

### 3-4. 管理者向け画面のナビゲーション（新規）

通報管理画面は、一般ユーザー向けのフッター5タブには含めない（一般ユーザーからは存在が見えない・辿り着けない導線とする）。マイページ画面に「通報管理」メニュー項目を設け、ログイン中ユーザーの `User.is_admin` が `true` の場合のみ表示する（`false`／未ログインの場合は非表示）。設計判断の理由は5章・6-9章・ADR-0007を参照。

#### RoundEvent（既存踏襲、意味論の明確化）

既存カラムに変更なし。ただし `current`（現在人数）の更新契機を明確化する。

| 項目 | 型 | 説明 |
|---|---|---|
| event_id | UUID | 募集ID |
| club_name | String | ゴルフ倶楽部名 |
| datetime | Datetime | 日時 |
| fee | Int | 費用 |
| capacity | Int | 募集人数 |
| current | Int | 現在人数（**参加申請が「承認」された時点でのみ加算。申請中は含めない**） |
| created_by | UUID | 作成者ID（主催者） |
| created_at | Datetime | 作成日 |

意味論変更の理由: PRDが「ラウンド募集参加承認後」のメッセージ開放を要求しており、これは参加に承認ステップが存在することを前提とする。既存の詳細設計書API（`POST /round-events/{id}/join`）は`current`を即時加算する実装だったが、UI文言は一貫して「参加**申請**」としており、承認ステップの存在を示唆していた。本書ではこの前提を明文化し、参加申請→承認のワークフローとして再定義する（ADR-0001参照）。

### 5-2. 新規モデル

#### AreaMaster（エリアマスタ）

| 項目 | 型 | 説明 |
|---|---|---|
| area_id | UUID | エリアID |
| prefecture | String | 都道府県（例: 埼玉県） |

#### MatchRequest（マッチング申請）

おすすめユーザー画面からの「マッチング申請（いいね）」を表すエンティティ。既存設計にはUI機能としてのみ存在し、データモデルが未定義だったため新設する。

| match_request_id | UUID | 申請ID |
| from_user_id | UUID | 申請者 |
| to_user_id | UUID | 申請先 |
| status | String(enum) | PENDING / ACCEPTED / REJECTED |
| created_at | Datetime | 申請日時 |
| responded_at | Datetime? | 承認・却下日時 |

制約: `(from_user_id, to_user_id)` の組み合わせでPENDING状態は1件まで（重複申請防止）。

#### RoundJoinRequest（ラウンド参加申請）

| 項目 | 型 | 説明 |
|---|---|---|
| join_request_id | UUID | 申請ID |

| user_id | UUID | 申請者 |

制約: 承認処理は `RoundEvent.capacity > RoundEvent.current` の場合のみ成立（既存バリデーションを承認タイミングに移動）。承認者は `RoundEvent.created_by` と一致するユーザーのみ。

#### Connection（メッセージ許可関係）

マッチング申請の承認、またはラウンド参加申請の承認によって自動生成される、2ユーザー間のメッセージ許可関係。メッセージのアクセス制御の起点となる。

| 項目 | 型 | 説明 |
|---|---|---|
| connection_id | UUID | ID |
| user_a_id | UUID | ユーザーA（`user_a_id < user_b_id` となるよう正規化し重複生成を防止） |
| user_b_id | UUID | ユーザーB |
| source_type | String(enum) | MATCH_REQUEST / ROUND_JOIN |
| source_id | UUID | 起点となった MatchRequest.match_request_id または RoundJoinRequest.join_request_id |
| created_at | Datetime | 作成日時（＝承認日時） |

設計意図: ラウンド募集は主催者と各参加者の間で個別にConnectionを作る（参加者同士のConnectionは自動生成しない。PRDの要求は「当該ユーザー間」であり主催者-参加者間の連絡が主目的のため。参加者同士のグループ的な連絡はPRD3-2章の「グループチャット等の高度化」に該当しPhase2以降）。同一ユーザーペアで複数回Connectionが成立しうる（例: マッチング承認後、別途ラウンドでも参加承認）が、メッセージ機能上はConnection単位でスレッドを分けず、ユーザーペア単位で1つの会話に統合する（7章UiState設計参照）。ユーザーペアに対し既にConnectionが存在する場合、新規承認イベントはConnectionを追加生成せず、メッセージ利用可否のみ維持する（重複スレッド防止）。

| 項目 | 型 | 説明 |
|---|---|---|

| sender_id | UUID | 送信者（user_a_idまたはuser_b_idのいずれか） |

| created_at | Datetime | 送信日時 |
| read_at | Datetime? | 受信者による既読日時（未読はnull） |

備考: `(user_a_id, user_b_id)` の正規化ペアで会話をグルーピングする。会話一覧はこのペア単位で最新メッセージを集約して表示する。

ステータス更新は、PRD 3-1章で新たにMustとされた通報管理（簡易管理画面）を通じて運営メンバーが行う（**確定**。詳細画面・APIは6-9章、権限管理はADR-0007参照）。旧版では管理画面の要否を「要確認事項」としていたが、プロダクトオーナー確認によりMVPスコープに含めることが確定したため、本書側で設計を追加した（10章参照）。ステータス名は簡易管理画面のPRD記載「未対応／対応中／対応済み」に合わせ、`PENDING`（未対応）→`REVIEWING`（対応中）→`RESOLVED`（対応済み・何らかの対応を行い完了）または`DISMISSED`（対応不要と判断し却下）という遷移を想定する。ただしMVPでは厳密な状態遷移バリデーション（逆行禁止等）は設けず、管理画面から任意のステータス値へ変更可能とする単純なAPIとする（過剰設計を避ける方針。6-9章）。凍結（`User.status=SUSPENDED`への変更）等の実対応そのものの自動化・専用APIはPRDで明確に将来検討とされているためスコープ外のまま維持する。

## 6. API設計拡張

既存API（`GET /round-events`, `POST /round-events`, `GET /users/recommend`, `GET /board`, `POST /board`, `GET /users/{id}`, `PUT /users/{id}`）は原則維持する。挙動変更のあるものは明記する。

認証: 本人確認完了後に発行されるアクセストークンを `Authorization: Bearer <token>` ヘッダーで送信する前提とする（新規、ADR-0003）。以下のAPI一覧で特記のないものは全て認証必須。

管理者API（6-9章）は、この同じBearerトークン認証基盤をそのまま流用し、トークンの持ち主である `User.is_admin` が `true` であることをサーバー側で追加検証する（`false`の場合は403）。管理者専用の別ログイン・別トークン方式は設けない（理由はADR-0007）。

### 6-1. 本人確認・認証（新規）

#### `POST /auth/phone/otp`
- 電話番号を指定しSMSでOTPを送信する
- パラメータ: `phone_number`
- 認証: 不要
- バリデーション: 同一電話番号への再送信は一定間隔（例: 60秒）を空ける

#### `POST /auth/phone/verify`
- OTPを検証し、あわせて当該電話番号が「新規（プロフィール未登録）」か「既存（登録済み）」かを判定し、判定結果に応じて認証まで完結させる（**変更**: 旧版は検証のみを行い`registration_token`のみを返していたが、新規/既存の判別責務がクライアント側に無いという設計漏れが発覚したため統合した。理由・経緯はADR-0006参照）
- パラメータ: `phone_number`, `otp_code`
- 認証: 不要
- サーバー側処理:
  1. `PhoneVerification` に対しOTPの正当性を検証する
  2. 検証成功時、`phone_number` が一致し `phone_verified=true` の `User` が既に存在するか判定する
  3. 存在する場合（既存ユーザー）: そのユーザーのセッションを開始し `access_token` を発行する（旧 `POST /auth/login` が行っていた処理をここに統合）
  4. 存在しない場合（新規ユーザー）: 本登録に進むための一時トークン `registration_token` を発行する
- レスポンス: `is_new_user: Boolean`（クライアントが分岐に用いる唯一の確定的な判定材料。他フィールドの有無による暗黙の分岐は行わない）
  - `is_new_user=true` の場合: `registration_token`（短期有効・アカウント未作成の状態でのみ使用）
  - `is_new_user=false` の場合: `user`（認証成功したユーザー本人）、`access_token`

#### `POST /users`（新規登録。既存設計に存在しなかったため新設）
- プロフィール初回登録とアカウント作成を兼ねる
- パラメータ: `registration_token`, `name`, `gender`, `age`, `area_id`, `average_score`, `purpose`, `introduction`
- レスポンス: 作成された `User`、以降のAPI利用に使う `access_token`
- 認証: 不要（`registration_token` が認証代わり）

#### `POST /auth/login`（**廃止**。ADR-0006）
旧版で定義していた「既存ユーザーの再ログイン」専用エンドポイントは廃止する。電話番号入力→OTP送信→OTP検証という画面フローは新規登録・再ログインの両方で同一であり、`POST /auth/phone/verify` の `is_new_user=false` 分岐がこの役割を代替する（同一OTPを2エンドポイントに渡す必要もなくなる）。旧版でこのエンドポイントに定めていた「レスポンスに`User`を含める」「暗黙のnullフォールバックを禁止する」という原則（ADR-0005）は、`POST /auth/phone/verify` の既存ユーザー分岐にそのまま引き継がれる。

### 6-9. 通報管理（簡易管理画面、新規）

PRD 3-1章「通報管理（簡易管理画面）」（Must、プロダクトオーナー確認により追加確定。10章参照）に対応するAPI群。想定利用者は `User.is_admin=true` の運営メンバーのみであり、認可は6章冒頭の方針（既存Bearerトークン + `is_admin`検証）に従う。設計判断の詳細はADR-0007を参照。

#### `PATCH /admin/reports/{id}/status`
- 通報のステータスを変更する
- パラメータ: `status`（PENDING/REVIEWING/RESOLVED/DISMISSEDのいずれか）、`handling_memo?`
- サーバー側処理: `Report.status` を更新し、`handled_by_user_id` に呼び出し元ユーザー、`handled_at` に現在時刻を設定。`handling_memo` が指定されていれば上書き保存する
- バリデーション: MVPでは状態遷移順序の強制は行わない（`status` に列挙値以外が指定された場合のみ400。過剰設計を避けるための単純化、ADR-0007参照）
- 認可: `is_admin=true` のみ
- 備考: 通報を受けたユーザーアカウントの凍結（`User.status=SUSPENDED`への変更）自体は、既存の`PUT /users/{id}`等の一般APIおよび本APIの対象外とする。PRDで「凍結等の実処理の自動化・高度化は将来検討」と明記されており、MVPでは対応方針の記録（本APIによるステータス・メモ更新）に留め、実際の凍結対応はDB直接操作等の運用でカバーする（過剰なAPI追加を避けるための意図的な判断）

## 8. 非機能要件への対応方針

| PRD該当項目 | 対応方針 |
|---|---|
| パフォーマンス（一覧系3秒以内目安） | 一覧系API（`/round-events`, `/users/recommend`, `/board`, `/conversations`）はページネーション対応を前提とし、初期表示は先頭ページのみ取得する。ブロックフィルタ等のサーバー側フィルタ処理はDB側インデックス（`blocker_user_id`等）で担保する。詳細なパフォーマンス要件・実測はDeveloperAgent／TesterAgentの検証対象とする |
| セキュリティ（TLS、個人情報の非開示） | 全通信TLS必須（NetworkModuleでhttps固定）。`GET /users/recommend` 等の一覧系レスポンスでは電話番号等の機微情報を含めず、必要な項目のみ返す設計とする。認証は6-1章のトークン方式 |
| プライバシー（住まいは市区町村粒度） | AreaMasterの `area_name` 粒度を市区町村相当に統一することで担保（GPS座標等は一切扱わない設計。既存設計・PRDと整合） |
| モデレーション運用（MVPは手動確認） | `Report.status`（PENDING/REVIEWING/RESOLVED/DISMISSED）で運営確認状況を表現し、確認・対応（ステータス変更・対応メモ記録）は6-9章の通報管理（簡易管理画面）で行う（**確定**。プロダクトオーナー確認によりMVPスコープに追加。10章参照） |
| 管理者向け機能の権限・認証（PRD5章） | 別建ての管理者認証基盤は設けず、既存のBearerトークン認証（ADR-0003）を流用し、`User.is_admin` フラグの有無をサーバー側で追加検証する方式とする（6-9章、ADR-0007）。想定利用者が少人数の運営メンバーのみというPRD方針を踏まえ、ロール・部署等の多段階権限は導入しない |
| 可用性（過度な冗長化は不要） | サーバーサイドはTypeScript(Node.js) + Cloud Functions for Firebase、DBはFirestoreを採用（**確定**。10章#6参照）。MVPでは単一リージョン・最小構成のサーバー構成を前提とし、詳細なインフラ設定（リージョン選定、スケーリング設定等）はDeveloperAgent着手時に別途検討する |

### 11-1. 差し戻し事項の反映（TesterAgent報告分）

TesterAgentの検証（`docs/test-plan.md` 4-1章）により、`POST /auth/login`のレスポンス定義漏れに起因する`AuthSession.userId`の空文字列フォールバック問題が発見された。ADR-0005のとおり是正した。DeveloperAgentは以下を修正すること（修正方針の詳細はADR-0005参照）。

| ファイル | 修正内容 |

| `app/src/main/java/com/golfmatch/app/data/dto/AuthDto.kt` | `AuthSessionResponseDto`のKDocコメントを更新し、「`user`は`POST /users`・`POST /auth/login`のいずれの成功レスポンスでも常に含まれる（nullableなのはJSONパース上の防御的措置であり、業務上nullは異常系）」旨を明記する |
| `app/src/main/java/com/golfmatch/app/data/api/ApiService.kt` | エンドポイント定義・戻り値型（`AuthSessionResponseDto`）は変更不要。KDocコメントで`login`のレスポンスに`user`が含まれる旨を明記するのみで良い |

## 12. サーバーサイド実装設計（Cloud Functions for Firebase）

### 12-0. 本章の位置づけ・前提

10章#6・#7で確定した「TypeScript(Node.js) + Cloud Functions for Firebase、DB: Firestore、SMS送信ベンダー: Twilio」を受け、サーバー実装（`functions/`配下）の内部設計を行う。6章のAPI仕様（エンドポイント・パラメータ・レスポンス・認可要件）は変更しない。本章はそれをどう実装するかのみを扱う。

**前提1: 5章のEntity定義は論理データモデル、Firestoreのドキュメント構造は物理スキーマ。** 5章の各Entityの項目は「APIレスポンスとして返る論理データモデル」の定義であり、Firestoreの実ドキュメントがそれと1対1である必要はない。クエリ簡略化・非正規化のための内部専用フィールド（例: 検索用に正規化したペアID等）をドキュメントに追加することは、5章の定義を「変更」したことにはならない。ただし5章で定義された項目をAPIレスポンスから欠落させることはない。

**前提2: Androidクライアントは常にCloud Functions経由でアクセスし、Firestoreに直接アクセスしない。** `NetworkModule.kt`のとおり、`ApiService`はRetrofit経由でCloud Functions（HTTPSトリガー）の単一ベースURL配下のRESTパスを呼び出す構成になっている。`FirebaseFirestore`のクライアントSDKインスタンスも同モジュールに存在するが、KDocの通り「今後直接利用する場合に備えて」提供されているだけで、現状の認証・データ取得フローでは使用されていない。本設計もこの前提を維持し、業務データへのアクセス経路をCloud Functions（Express経由のREST API）に一本化する。これにより後述のFirestoreセキュリティルール（12-7章）を大幅に単純化できる。

### 12-1. ディレクトリ構成（`functions/`配下）

#### 方針: サーバー側にAndroidクライアントと同等のClean Architectureレイヤー分割は持ち込まない

Androidクライアント側（2章・4章）は `ui/domain/data/di` の4層構成とHiltによるDIを採用しているが、これはAndroid特有の事情（UIフレームワーク依存の分離、ネットワーク/ローカルキャッシュ等データソースの切り替え、テスト時のモック差し替え）に根ざした設計であり、サーバー側にそのまま持ち込む合理性はないと判断する。理由は以下のとおり。

- データソースが最初からFirestore1つに固定されており、将来的に差し替える計画もない（Androidの`data/repository/impl`が想定する「複数データソースの抽象化」という課題がサーバー側には存在しない）
- ローカル開発・動作確認にFirebase Emulator Suiteの実Firestoreエミュレータを使う前提（12-8章）のため、Androidのテストで必要になるような「Repositoryインターフェースをモックに差し替える」動機が薄い（サービス層のテストは実Firestore（エミュレータ）に対して行うほうが本番との乖離が少なく、むしろ好ましい）
- 少人数運営・MVP規模のプロジェクトにおいて、`domain`層のユースケース・リポジトリインターフェース・`data`層の実装・DIコンテナという4層をサーバー側にも複製すると、1エンドポイントの実装に対するファイル数・ボイラープレートが増え、ADR-0007等でも一貫して採用してきた「過剰設計を避ける」方針に反する

一方で、**SMS送信（Twilio）だけは意図的にインターフェースを切る**（12-5章）。これはAndroid側の「複数データソースの抽象化」とは異なり、「実アカウント未用意のため実装を差し替える必要がある」という具体的な要求が今回存在するためであり、レイヤー分割を一般原則として持ち込むわけではない。

#### 採用する構成: 機能単位モジュール分割 + Express製の単一HTTPS関数

`ApiService.kt`のベースURLが`.../api/`という単一パス配下に全REST操作をぶら下げる構成になっていることから、クライアント側の想定と一致させるため、Cloud Functions側もエンドポイントごとに関数を分けるのではなく、**Express製の1アプリケーションを`api`という単一のHTTPS関数としてデプロイし、Express Routerで機能ごとにルーティングを分ける**方式を採用する。

理由:
- エンドポイントごとに個別のCloud Functionを立てる方式（例: `exports.getRoundEvents = functions.https.onRequest(...)`を6章のエンドポイント数だけ用意）は、関数ごとのコールドスタートが増え、ローカルエミュレータでの起動・デプロイの単位も煩雑になる
- 単一のExpressアプリであれば、`NetworkModule.kt`のBASE_URL（`.../api/`）+ Retrofitの相対パス（`auth/phone/otp`等）の組み合わせと、そのままExpressのルーティングパスが対応し、クライアント・サーバー間のパスの対応関係が分かりやすい
- ミドルウェア（認証・エラーハンドリング・共通レスポンス整形）をExpressの仕組みでアプリ全体に一括適用でき、機能ごとの重複実装を避けられる

### 12-2. Firestoreコレクション設計

#### 12-2-1. ドキュメントID戦略（共通方針）

- 各Entityの主キー（`user_id`, `event_id`等）は `crypto.randomUUID()` で生成したUUID文字列を用い、Firestoreのドキュメント自動採番IDは使わない（5章のEntity定義がUUID型を明記しているため、型定義との一貫性を優先する）
- **2者間の関係を表すEntity（Connection, Block）は、正規化した決定的なペア文字列をドキュメントIDとして用いる。** これにより「重複生成防止のためのクエリ」が不要になり（IDが同じなら`create()`が自然に失敗する/`set(merge)`で冪等になる）、かつ「関係が存在するか」の判定が検索ではなく1回のポイントGetで済む（クエリよりレイテンシ・コストの面で有利）。詳細は各Entityの節を参照

#### 12-2-2. コレクション一覧・Entityマッピング

| コレクション | パス | ドキュメントID | 対応Entity（5章） | Phase |
|---|---|---|---|---|
| users | `users/{userId}` | `crypto.randomUUID()` | User | 1（block関連フィールドの参照はPhase3から） |
| areaMasters | `areaMasters/{areaId}` | `crypto.randomUUID()` | AreaMaster | 1 |
| phoneVerifications | `phoneVerifications/{phoneHash}` | `sha256(phone_number)`（下記参照） | PhoneVerification | 1 |
| sessions | `sessions/{tokenHash}` | `sha256(raw access_token)` | （新規、Bearerトークン実装の内部モデル。12-3章） | 1 |
| roundEvents | `roundEvents/{eventId}` | `crypto.randomUUID()` | RoundEvent | 1 |
| roundEvents/{eventId}/joinRequests | `roundEvents/{eventId}/joinRequests/{requestId}` | `crypto.randomUUID()` | RoundJoinRequest | 1 |
| matchRequests | `matchRequests/{matchRequestId}` | `crypto.randomUUID()` | MatchRequest | 2 |
| connections | `connections/{pairId}` | `min(userAId,userBId)_max(userAId,userBId)` | Connection | 1（先行実装。13-3章） |
| messages | `messages/{messageId}` | `crypto.randomUUID()` | Message | 3 |
| boardPosts | `boardPosts/{postId}` | `crypto.randomUUID()` | BoardPost | 2 |
| reports | `reports/{reportId}` | `crypto.randomUUID()` | Report | 3 |
| blocks | `blocks/{blockPairId}` | `${blockerUserId}_${blockedUserId}`（方向あり） | Block | 3 |

補足（`phoneVerifications`のドキュメントID）: 電話番号（PII）をそのままドキュメントIDに使うとログ等に生の電話番号が残りやすいため、`sha256`ハッシュをIDとする。1電話番号につき常に1ドキュメントとし、`POST /auth/phone/otp`が呼ばれるたびに上書きする（過去のOTPは無効化される想定と一致する）。これにより「電話番号でPENDING中のOTPを検索する」クエリ自体が不要になり、複合インデックスも不要になる。同一ドキュメントの`created_at`を見れば「60秒以内の再送信か」の判定（6-1章バリデーション）もクエリなしで行える。

#### 12-2-3. 個別Entityの補足設計

**Connection（`connections/{pairId}`）**
`pairId = [userAId, userBId].sort().join('_')`。この決定的IDにより、
- マッチング承認・ラウンド参加承認のたびにConnectionを新規作成しようとする処理は、既存ドキュメントがあれば作成せずスキップする（`set(..., { merge: false })`をtry/catchするか、事前に`get()`して存在確認する）だけで冪等に実装でき、5章のConnectionの設計意図（「同一ペアに対し重複生成しない」）をクエリなしで満たせる
- メッセージ送信APIの認可チェック（「相手とConnectionがあるか」）も、`connections/{pairId}`への1回のGetで済む（クエリではなくポイントGetのため高速・低コスト）
- ブロック関係チェック（後述）と合わせて、認証・認可ミドルウェア側の共通ヘルパーとして提供する（12-4章）

**Block（`blocks/{blockerUserId}_{blockedUserId}`）**
方向性があるため正規化はしない。「AがBをブロックしたか」は`blocks/{A}_{B}`への1回のGetで判定できる。「AB間にブロック関係があるか（双方向）」は`blocks/{A}_{B}`と`blocks/{B}_{A}`の2回のGetで判定する（クエリ不要）。

一覧系API（`GET /round-events`, `GET /users/recommend`, `GET /board`）のブロック除外フィルタは、Firestoreクエリの`not-in`演算子（最大10件までしか指定できない制約がある）に頼らず、**アプリケーションコード側でのフィルタリング**を採用する。具体的には、リクエストユーザーのブロック関連ID集合（`blocks`を`blocker_user_id==me`・`blocked_user_id==me`の2クエリで取得しUnionを取る）を一度取得し、一覧クエリの結果に対しメモリ上で除外する。MVP規模（少人数運営、ブロック件数も少数と想定）ではこの方式で十分であり、`not-in`の10件上限や複合インデックスの複雑化を避けられる。将来的にユーザー数・ブロック件数が増えた場合はページネーションとの整合性を含め再検討が必要になる点は既知の制約として残す。

**Message（`messages/{messageId}`）**
5章の項目（`user_a_id`, `user_b_id`, `sender_id`, `content`, `created_at`, `read_at`）に加え、Firestore内部専用フィールドとして`pairId`（Connectionと同じ正規化ペアキー）を追加する。会話スレッド取得（`GET /conversations/{partnerId}/messages`）のクエリを`where pairId == X order by createdAt desc`という2フィールドのみの条件にできるため、`user_a_id`・`user_b_id`の2フィールドで絞り込む場合より複合インデックスがシンプルになる（12-2-5章参照）。`pairId`はAPIレスポンスには含めない内部実装詳細。

**Connectionへの会話プレビュー情報の非正規化（`GET /conversations`用）**
`GET /conversations`は「相手ユーザー概要・最新メッセージプレビュー・未読件数・最終更新日時」を一覧で返す必要がある（6-7章）。これを毎回「自分のConnection一覧を取得→各Connectionごとに最新メッセージを個別取得→未読数を個別カウント」という形で実装するとConnection数に比例したクエリが発生する。本設計では、`connections/{pairId}`ドキュメントに以下を非正規化して持たせる。

| フィールド | 説明 |
|---|---|
| lastMessageAt | 最終メッセージ送信日時（一覧のソートキーにも使う） |
| lastMessagePreview | 最終メッセージ本文の先頭一部 |
| unreadCountForUserA / unreadCountForUserB | `user_a_id`/`user_b_id`それぞれから見た未読件数 |

`POST /conversations/{partnerId}/messages`（メッセージ送信）はFirestoreトランザクション内で、(1)ブロック関係・Connection存在チェック、(2)`messages`への新規ドキュメント作成、(3)`connections/{pairId}`の上記非正規化フィールド更新、を同時に行う（送信APIは元々Connection存在チェックのため`connections`ドキュメントを読む必要があり、同一トランザクション内での追加更新は実装コストが小さい）。`POST /conversations/{partnerId}/read`は該当する`unreadCountForUser*`を0に戻す。

一方、通報管理一覧（`GET /admin/reports`）の`target_summary`（対象ユーザー名/アイコン、または投稿冒頭）は非正規化しない。管理画面の利用頻度・一覧件数はごく少数（少人数運営、通報自体が高頻度に発生する想定ではない）であり、`reports`一覧取得後に対象User/BoardPostドキュメントを`getAll()`でバッチ取得して都度合成する方式で十分であり、通報後にユーザー名やアイコンが変わった場合にも常に最新の情報が表示されるという利点もある。

#### 12-2-4. 複合インデックスが必要になる一覧系クエリ

| コレクション | クエリ | 必要な複合インデックス |
|---|---|---|
| areaMasters | `GET /areas`: `is_active==true` かつ `display_order`昇順 | `(isActive ASC, displayOrder ASC)` |
| roundEvents/{eventId}/joinRequests | 参加申請の重複防止チェック: `user_id==X` かつ `status==PENDING` | `(userId ASC, status ASC)`（サブコレクション単位） |
| matchRequests | 重複PENDING申請チェック: `from_user_id==X` かつ `to_user_id==Y` かつ `status==PENDING` | `(fromUserId ASC, toUserId ASC, status ASC)` |
| matchRequests | `GET /users/me/match-requests?direction=received`: `to_user_id==me` 、`created_at`降順 | `(toUserId ASC, createdAt DESC)` |
| matchRequests | `direction=sent`: `from_user_id==me`、`created_at`降順 | `(fromUserId ASC, createdAt DESC)` |
| messages | `GET /conversations/{partnerId}/messages`: `pairId==X`、`created_at`降順＋カーソルページネーション | `(pairId ASC, createdAt DESC)` |
| reports | `GET /admin/reports?status=X`: `status==X`、`created_at`降順 | `(status ASC, createdAt DESC)` |

`roundEvents`（一覧）、`boardPosts`（一覧）、`blocks`（自分のブロック一覧）は単一フィールドの等価/ソート条件のみのためFirestoreの自動インデックスで足り、複合インデックス定義は不要と判断する（前述のとおりブロック除外はアプリケーションコード側で行うため、`not-in`起因の複合インデックスは発生しない）。

### 12-3. Bearerトークンの実装方式

**結論: 自己発行の不透明トークン（opaque token）＋ Firestoreセッションストア（`sessions`コレクション）を採用する。** 判断の詳細な比較・理由はADR-0008を参照。ここでは実装仕様のみ記す。

- トークン生成: `crypto.randomBytes(32).toString('base64url')`（256bitのランダム値）
- 保存: 生トークンはどこにも保存しない。`sha256(rawToken)`のハッシュ値をドキュメントIDとして`sessions/{tokenHash}`に`userId`, `createdAt`, `expiresAt`を保存する（`PhoneVerification`のOTPハッシュ化と同じ考え方）
- クライアントに返す`access_token`（`POST /users`・`POST /auth/phone/verify`の既存ユーザー分岐）は生トークンそのもの。以降クライアントはこれをそのまま`Authorization: Bearer <access_token>`として送信する（現状の`NetworkModule`・`AuthSessionManager`の実装はこの前提で既に成立しており、クライアント側の追加実装は不要）
- 有効期限: 発行から90日。クライアント側に明示的なリフレッシュ機構・ログアウトAPIは定義されていない（`AuthSessionManager`はプロセス内メモリ保持のみでアプリ再起動時に実質再ログインとなる）ため、サーバー側の期限は「長期間放置されたトークンを無効化する」ための保険的な上限という位置づけとし、短命化・リフレッシュ設計は行わない（過剰設計の回避）

### 12-4. 認証・認可ミドルウェアの設計

#### `authenticate`ミドルウェア（全モジュール共通）
1. `Authorization: Bearer <token>`ヘッダーを取得。無ければ401（`UNAUTHENTICATED`）
2. `sha256(token)`で`sessions/{tokenHash}`をGet。存在しない、または`expires_at`が過去なら401
3. `sessions.userId`から`users/{userId}`をGet。存在しない、または`status==SUSPENDED`なら401（凍結アカウントは即座にアクセス不可にする。運用者がDBを直接`status=SUSPENDED`に更新した場合、`sessions`ドキュメント自体を消さなくても次のリクエストから即座に効力を持つ。これは「User存在確認のためのFirestore読み取りをどのみち行う」設計だからこそ、追加のセッション失効処理を書かずに実現できる副次的な利点である）
4. 解決した`User`を`req.currentUser`にセットし次のミドルウェア/ハンドラへ

`POST /auth/phone/otp`, `POST /auth/phone/verify`, `POST /users`, `GET /areas`（6章の認証不要エンドポイント）にはこのミドルウェアを適用しない。

#### `requireAdmin`ミドルウェア（`/admin/*`配下のみ）
`authenticate`の後段に追加で挟む。`req.currentUser.isAdmin !== true`なら403（`FORBIDDEN`）。ADR-0007の方針（別建て管理者認証基盤を持たない）に従い、`authenticate`が解決した同じ`User`のフラグを見るだけの薄い実装とする。

#### ブロック関係チェックの共通化
`connections`モジュールに`assertNotBlocked(userIdA, userIdB): Promise<void>`ヘルパーを設け、`blocks/{A}_{B}`・`blocks/{B}_{A}`の2点Getでいずれかが存在すれば`AppError(403, 'BLOCKED')`を投げる。マッチング申請作成・ラウンド参加申請作成・メッセージ送信の各`service.ts`から共通で呼び出す（5-2章Block「効果」の一覧に対応）。一覧系API（recommend/board/round-events）のブロック除外は12-2-3章のとおりアプリケーションコード側のフィルタ関数（`excludeBlockedUsers`）として共通化し、こちらも`connections`または新設の`blocks`モジュールに置く。

### 12-5. SMS送信（Twilio）の抽象化方針

Twilioアカウントが未用意のため、以下のインターフェースを切り実装を差し替え可能にする。

```typescript
export interface SmsSender {
  send(phoneNumber: string, body: string): Promise<void>;
}
```

- `TwilioSmsSender`: `twilio` npmパッケージを用いた実装。認証情報（`TWILIO_ACCOUNT_SID` / `TWILIO_AUTH_TOKEN` / `TWILIO_FROM_NUMBER`）はCloud Functionsのシークレット（Firebase Functions v2の`defineSecret`、もしくはローカルでは`.env`）から読み込む。実アカウント確保後に有効化する想定で、今回のスコープでは実際に呼び出されることはない
- `ConsoleSmsSender`: 送信内容（宛先電話番号・OTPコード）を`console.log`するのみのダミー実装。ローカル開発・Emulator Suiteでの動作確認はこちらを使う
- 実装の選択は`sms/index.ts`の`getSmsSender()`が行う。Firebase Emulator Suiteは環境変数`FUNCTIONS_EMULATOR=true`を自動的に設定するため、これを検知した場合は自動的に`ConsoleSmsSender`を返す。加えて明示的な上書き用に環境変数`SMS_PROVIDER=console|twilio`も用意し、エミュレータ外でもダミー実装を強制できるようにする
- `auth.service.ts`（`POST /auth/phone/otp`の処理）は`SmsSender`インターフェースにのみ依存し、具体実装を知らない。これにより将来Twilioアカウントを確保した際も`auth.service.ts`側の変更は不要

### 12-6. エラーハンドリング・レスポンス形式の統一方針

- 成功レスポンス: 6章で定義された各APIのレスポンス形（`User`, `RoundEvent[]`等）をそのままJSONボディとして返す（エンベロープ等の追加ラップはしない。既存クライアント側のDTOがこの前提で実装済みのため）
- エラーレスポンス: 統一形式 `{ "error": { "code": string, "message": string } }` を用いる。`code`はプログラムで分岐可能な識別子（例: `VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `BLOCKED`, `RATE_LIMITED`, `INTERNAL`）、`message`はログ・デバッグ用の説明文（クライアントUIは現状サーバーのエラーメッセージをそのまま表示する設計にはなっていないため、日本語/英語の統一は必須要件ではないが、開発効率上日本語で統一する）
- 実装: 業務エラーは`AppError`（`httpStatus`, `code`, `message`を持つクラス）をthrowすることで表現し、Express共通の`errorHandler`ミドルウェアで捕捉し上記形式に変換する。`AppError`以外の未捕捉例外は500・`code=INTERNAL`として返し、詳細はCloud Loggingにのみ出力してレスポンスには含めない（内部実装詳細の漏洩防止）
- 各routeハンドラは`asyncHandler`でラップし、`try/catch`の重複記述を避ける

### 12-7. Firestoreセキュリティルールの方針

12-0章の前提2のとおり、Androidクライアントは業務データについてFirestoreに直接アクセスせず、常にCloud Functions（Admin SDK、セキュリティルールをバイパスする信頼された実行コンテキスト）経由でアクセスする。そのため、Firestoreセキュリティルールに認可ロジック（`is_admin`判定等）を持たせる必要がない。ルールは原則として全コレクションを`allow read, write: if false;`とし、クライアントからの直接アクセスを一律拒否する単純な構成とする。認可判定はすべて12-4章のミドルウェアに一元化する。

### 12-8. ローカル開発・動作確認方針（Firebase Emulator Suite）

実Twilioアカウント・実SMS送信の動作確認は今回のスコープ外（10章参照）。ローカルではFirebase Emulator Suiteを用いて以下を起動し、Cloud Functions・Firestore・（将来的なFirebase Auth直接利用に備えた）Authエミュレータの3つで動作確認を行う。

| エミュレータ | 用途 |
|---|---|
| Functions | `functions/`のExpressアプリ（`api`関数）をローカル実行し、Android実機/エミュレータの`NetworkModule.BASE_URL`をローカルエミュレータのURLに向けて疎通確認する |
| Firestore | 全コレクションの読み書きをローカルで完結させる。エミュレータ起動時は空のため、`areaMasters`の初期データ投入用シードスクリプト（例: `npm run seed:areas`）を用意する（登録フローの動作確認に必須のため） |
| Auth | 本設計（独自Bearerトークン方式、ADR-0008）では現時点で必須ではないが、`NetworkModule.kt`が将来のFirebase Auth直接利用に備え`FirebaseAuth`インスタンスを保持している経緯（コメント参照）を踏まえ、起動コストがほぼ無いことも考慮し念のため起動対象に含めておく |

OTP検証フローの動作確認は、`POST /auth/phone/otp`呼び出し時に`ConsoleSmsSender`がFunctionsエミュレータのログにOTPコードを出力するため、それを読み取って`POST /auth/phone/verify`に手動で入力する（curl・Postman等、またはAndroidアプリからの実操作のいずれでも可）。実SMS受信は発生しないため、Android実機・エミュレータどちらでも同一の手順で確認できる。

## 13. サーバー実装フェーズ計画

### 13-1. フェーズ区切りの技術的評価

指示された3フェーズ区切り（Phase1: 認証・エリアマスタ・ユーザープロフィール・ラウンド募集／Phase2: おすすめユーザー・マッチング申請・掲示板／Phase3: メッセージ・通報・ブロック・通報管理）は、技術的に妥当と判断する。

- Phase1は「認証基盤＋ユーザーの実体」という以降の全フェーズが依存する土台であり、最初に実装する必要がある
- Phase2（発見・マッチング系）とPhase3（安全・コミュニケーション系）は機能としては独立度が高いが、Phase3のメッセージ機能はPhase1・Phase2それぞれの「承認」イベント（ラウンド参加承認・マッチング承認）が生成する`Connection`に依存するため、Phase3を最後に置く区切りは自然である
- ただし、この依存関係により**Phase1・Phase2の実装時点でConnection関連のデータモデル・書き込みロジックを先行して用意しておく必要がある**（13-3章）。これは新規追加ではなく、6-4章・6-5章の承認APIの実装に元々含まれている処理であるため、フェーズ区切り自体の見直しは不要と判断する

| 依存元 | 依存先 | 内容 |

| Phase3（ブロック機能） | Phase1（`GET /round-events`）・Phase2（`GET /users/recommend`, `GET /board`） | 5-2章のBlockの効果（一覧系APIからのブロック対象除外）は、`blocks`コレクション自体がPhase3で新設されるため、Phase1・Phase2の実装時点では効果を持たない（`blocks`が空でありフィルタが実質no-opになる）。Phase3実装時に、既存のPhase1・Phase2の一覧クエリ処理へブロック除外フィルタ（12-2-3章の`excludeBlockedUsers`）を追加する改修が必要になる。新規エンドポイント追加ではなく既存コードの改修を伴う点に注意する |
| Phase2・Phase3全般 | Phase1（認証基盤） | `authenticate`ミドルウェア（12-4章）はPhase1で完成させる必要があり、Phase2・Phase3の全エンドポイントがこれに依存する |

以上より、DeveloperAgentはPhase1着手時点で「認証基盤」「エリアマスタ」「ユーザープロフィール」「ラウンド募集（申請→承認、Connection生成含む）」に加え、12-1章の`connections`共通モジュールまでを実装範囲に含めること。Twilio実SMS送信・実デプロイ・実機SMS受信確認は本エンゲージメントのスコープ外（10章参照）であり、Emulator Suite上での動作確認（12-8章）までを完了の基準とする。
