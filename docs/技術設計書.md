## 1. システム概要（既存踏襲）

本アプリは、ゴルフプレイヤー同士のマッチング、ラウンド募集、掲示板投稿、プロフィール管理を行うコミュニティサービスである。目的は、ゴルフ仲間の発見、ラウンド参加の促進、コミュニティ形成である（既存設計書 1章を継承、変更なし）。

PRDにより、以下がMVPスコープに追加された。
- ラウンド参加承認後・マッチング申請承認後の当事者間メッセージ
- 通報・ブロックによる安全機能
- 登録時のSMS等による簡易本人確認
- 将来のエリア拡大に耐えるエリアマスタ管理

対象OS: MVPはAndroidのみ（PRD 5章に準拠、既存設計に変更なし）。

## 2. アーキテクチャ方針（既存踏襲）

- **MVVM + Container + Hilt + Clean Architecture**（既存設計書 3章を継承）
- UI とロジックを完全分離。ViewModel は UiState（不変データクラス）を `StateFlow` で公開し、Container が Screen に橋渡しする
- 依存注入は Hilt を使用
- レイヤー責務（既存踏襲）
  - `ui/` : 画面表示・ユーザー操作の受付のみ。ビジネスロジックを持たない
  - `domain/` : ビジネスモデル・リポジトリインターフェース・ユースケース（フレームワーク非依存）
  - `data/` : API通信、DTO、DTO⇔Domainモデルのマッピング、リポジトリ実装
  - `di/` : Hiltモジュール

**拡張方針**: 新機能（メッセージ／通報・ブロック／本人確認／エリアマスタ）もこのレイヤー構成・命名規則を踏襲する。新規に導入するモジュール（認証層）についても同じ4層構成に従う。

既存設計にはAPI認証・セッション管理の定義が存在しない（`ApiService.kt` にトークンの概念がない）。本人確認機能の追加に伴い、最低限の認証基盤を新設する必要がある。詳細は ADR-0003 を参照。

サーバーサイドの実行環境は TypeScript(Node.js) + Cloud Functions for Firebase、DBは Firestore を採用する（**確定**。プロダクトオーナー確認、10章#6参照）。本書はモバイルアプリ側のアーキテクチャ・API仕様（インターフェース契約）を主眼とし、サーバー実装の詳細設計（関数分割、Firestoreのコレクション設計・インデックス設計等）はDeveloperAgent着手時に別途行う。

### 3-3. メッセージ機能のナビゲーション位置（確定）

メッセージ一覧画面はフッターメニュー5番目のタブとして追加する（5タブ化）。プロダクトオーナー確認により、暫定推奨案のまま正式採用が確定した（未読件数のバッジ表示など、メッセージ機能の可視性を担保するため）。既存4タブ（ホーム／おすすめユーザー／掲示板／マイページ）はそのままの並びを維持し、5番目に「メッセージ」タブを追加する。API・データモデル・画面遷移はもともと両パターンに対応可能な形で設計していたため、本決定に伴う設計変更は発生しない。

### 3-4. 管理者向け画面のナビゲーション（新規）

通報管理画面は、一般ユーザー向けのフッター5タブには含めない（一般ユーザーからは存在が見えない・辿り着けない導線とする）。マイページ画面に「通報管理」メニュー項目を設け、ログイン中ユーザーの `User.is_admin` が `true` の場合のみ表示する（`false`／未ログインの場合は非表示）。設計判断の理由は5章・6-9章・ADR-0007を参照。

#### RoundEvent（既存踏襲、意味論の明確化）

既存カラムに変更なし。ただし `current`（現在人数）の更新契機を明確化する。

| 項目 | 型 | 説明 |
|---|---|---|
| event_id | UUID | 募集ID |
| club_name | String | ゴルフ倶楽部名 |
| datetime | Datetime | 日時 |
| fee | Int | 費用 |
| capacity | Int | 募集人数 |
| current | Int | 現在人数（**参加申請が「承認」された時点でのみ加算。申請中は含めない**） |
| created_by | UUID | 作成者ID（主催者） |
| created_at | Datetime | 作成日 |

意味論変更の理由: PRDが「ラウンド募集参加承認後」のメッセージ開放を要求しており、これは参加に承認ステップが存在することを前提とする。既存の詳細設計書API（`POST /round-events/{id}/join`）は`current`を即時加算する実装だったが、UI文言は一貫して「参加**申請**」としており、承認ステップの存在を示唆していた。本書ではこの前提を明文化し、参加申請→承認のワークフローとして再定義する（ADR-0001参照）。

#### Connection（メッセージ許可関係）

| 項目 | 型 | 説明 |

| connection_id | UUID | ID |
| user_a_id | UUID | ユーザーA（`user_a_id < user_b_id` となるよう正規化し重複生成を防止） |
| user_b_id | UUID | ユーザーB |
| source_type | String(enum) | MATCH_REQUEST / ROUND_JOIN |
| source_id | UUID | 起点となった MatchRequest.match_request_id または RoundJoinRequest.join_request_id |
| created_at | Datetime | 作成日時（＝承認日時） |

設計意図: ラウンド募集は主催者と各参加者の間で個別にConnectionを作る（参加者同士のConnectionは自動生成しない。PRDの要求は「当該ユーザー間」であり主催者-参加者間の連絡が主目的のため。参加者同士のグループ的な連絡はPRD3-2章の「グループチャット等の高度化」に該当しPhase2以降）。同一ユーザーペアで複数回Connectionが成立しうる（例: マッチング承認後、別途ラウンドでも参加承認）が、メッセージ機能上はConnection単位でスレッドを分けず、ユーザーペア単位で1つの会話に統合する（7章UiState設計参照）。ユーザーペアに対し既にConnectionが存在する場合、新規承認イベントはConnectionを追加生成せず、メッセージ利用可否のみ維持する（重複スレッド防止）。

## 6. API設計拡張

既存API（`GET /round-events`, `POST /round-events`, `GET /users/recommend`, `GET /board`, `POST /board`, `GET /users/{id}`, `PUT /users/{id}`）は原則維持する。挙動変更のあるものは明記する。

認証: 本人確認完了後に発行されるアクセストークンを `Authorization: Bearer <token>` ヘッダーで送信する前提とする（新規、ADR-0003）。以下のAPI一覧で特記のないものは全て認証必須。

管理者API（6-9章）は、この同じBearerトークン認証基盤をそのまま流用し、トークンの持ち主である `User.is_admin` が `true` であることをサーバー側で追加検証する（`false`の場合は403）。管理者専用の別ログイン・別トークン方式は設けない（理由はADR-0007）。

### 6-1. 本人確認・認証（新規）

#### `POST /auth/phone/otp`
- 電話番号を指定しSMSでOTPを送信する
- パラメータ: `phone_number`
- 認証: 不要
- バリデーション: 同一電話番号への再送信は一定間隔（例: 60秒）を空ける

#### `POST /auth/phone/verify`
- OTPを検証し、あわせて当該電話番号が「新規（プロフィール未登録）」か「既存（登録済み）」かを判定し、判定結果に応じて認証まで完結させる（**変更**: 旧版は検証のみを行い`registration_token`のみを返していたが、新規/既存の判別責務がクライアント側に無いという設計漏れが発覚したため統合した。理由・経緯はADR-0006参照）
- パラメータ: `phone_number`, `otp_code`
- 認証: 不要
- サーバー側処理:
  1. `PhoneVerification` に対しOTPの正当性を検証する
  2. 検証成功時、`phone_number` が一致し `phone_verified=true` の `User` が既に存在するか判定する
  3. 存在する場合（既存ユーザー）: そのユーザーのセッションを開始し `access_token` を発行する（旧 `POST /auth/login` が行っていた処理をここに統合）
  4. 存在しない場合（新規ユーザー）: 本登録に進むための一時トークン `registration_token` を発行する
- レスポンス: `is_new_user: Boolean`（クライアントが分岐に用いる唯一の確定的な判定材料。他フィールドの有無による暗黙の分岐は行わない）
  - `is_new_user=true` の場合: `registration_token`（短期有効・アカウント未作成の状態でのみ使用）
  - `is_new_user=false` の場合: `user`（認証成功したユーザー本人）、`access_token`

#### `POST /users`（新規登録。既存設計に存在しなかったため新設）
- プロフィール初回登録とアカウント作成を兼ねる
- パラメータ: `registration_token`, `name`, `gender`, `age`, `area_id`, `average_score`, `purpose`, `introduction`
- レスポンス: 作成された `User`、以降のAPI利用に使う `access_token`
- 認証: 不要（`registration_token` が認証代わり）

#### `POST /auth/login`（**廃止**。ADR-0006）
旧版で定義していた「既存ユーザーの再ログイン」専用エンドポイントは廃止する。電話番号入力→OTP送信→OTP検証という画面フローは新規登録・再ログインの両方で同一であり、`POST /auth/phone/verify` の `is_new_user=false` 分岐がこの役割を代替する（同一OTPを2エンドポイントに渡す必要もなくなる）。旧版でこのエンドポイントに定めていた「レスポンスに`User`を含める」「暗黙のnullフォールバックを禁止する」という原則（ADR-0005）は、`POST /auth/phone/verify` の既存ユーザー分岐にそのまま引き継がれる。

### 6-9. 通報管理（簡易管理画面、新規）

PRD 3-1章「通報管理（簡易管理画面）」（Must、プロダクトオーナー確認により追加確定。10章参照）に対応するAPI群。想定利用者は `User.is_admin=true` の運営メンバーのみであり、認可は6章冒頭の方針（既存Bearerトークン + `is_admin`検証）に従う。設計判断の詳細はADR-0007を参照。

#### `GET /admin/reports`
- 通報一覧取得（管理者向け）
- クエリパラメータ: `status?`（PENDING/REVIEWING/RESOLVED/DISMISSEDのいずれか、絞り込み。未指定時は全件）、ページネーション（`before`, `limit`。既存一覧APIと同様の方式）
- レスポンス: `Report[]`（`reporter`・通報対象の要約（`target_summary`: USERなら対象ユーザーの氏名・アイコン、BOARD_POSTなら投稿者氏名・本文冒頭）を含めて一覧表示に必要な情報を1回の呼び出しで取得できるようにする）
- 認可: `is_admin=true` のみ（`false`は403）
- 並び順: `created_at` 降順（未対応の通報が埋もれないよう、UI側は既定で `status=PENDING` フィルタを推奨するが、これは画面側の初期状態の話でありAPI側の必須要件ではない）

#### `GET /admin/reports/{id}`
- 通報詳細取得（管理者向け）
- レスポンス: `Report` 全項目に加え、通報者(`reporter`)・通報対象の詳細（`target_detail`: USERなら`User`のプロフィール一式（`phone_number`等の機微情報は含めない。8章の非機微情報方針を踏襲）、BOARD_POSTなら投稿本文全文・投稿者情報）を展開する
- 認可: `is_admin=true` のみ

#### `PATCH /admin/reports/{id}/status`
- 通報のステータスを変更する
- パラメータ: `status`（PENDING/REVIEWING/RESOLVED/DISMISSEDのいずれか）、`handling_memo?`
- サーバー側処理: `Report.status` を更新し、`handled_by_user_id` に呼び出し元ユーザー、`handled_at` に現在時刻を設定。`handling_memo` が指定されていれば上書き保存する
- バリデーション: MVPでは状態遷移順序の強制は行わない（`status` に列挙値以外が指定された場合のみ400。過剰設計を避けるための単純化、ADR-0007参照）
- 認可: `is_admin=true` のみ
- 備考: 通報を受けたユーザーアカウントの凍結（`User.status=SUSPENDED`への変更）自体は、既存の`PUT /users/{id}`等の一般APIおよび本APIの対象外とする。PRDで「凍結等の実処理の自動化・高度化は将来検討」と明記されており、MVPでは対応方針の記録（本APIによるステータス・メモ更新）に留め、実際の凍結対応はDB直接操作等の運用でカバーする（過剰なAPI追加を避けるための意図的な判断）

## 8. 非機能要件への対応方針

| PRD該当項目 | 対応方針 |
|---|---|
| パフォーマンス（一覧系3秒以内目安） | 一覧系API（`/round-events`, `/users/recommend`, `/board`, `/conversations`）はページネーション対応を前提とし、初期表示は先頭ページのみ取得する。ブロックフィルタ等のサーバー側フィルタ処理はDB側インデックス（`blocker_user_id`等）で担保する。詳細なパフォーマンス要件・実測はDeveloperAgent／TesterAgentの検証対象とする |
| セキュリティ（TLS、個人情報の非開示） | 全通信TLS必須（NetworkModuleでhttps固定）。`GET /users/recommend` 等の一覧系レスポンスでは電話番号等の機微情報を含めず、必要な項目のみ返す設計とする。認証は6-1章のトークン方式 |
| プライバシー（住まいは市区町村粒度） | AreaMasterの `area_name` 粒度を市区町村相当に統一することで担保（GPS座標等は一切扱わない設計。既存設計・PRDと整合） |
| モデレーション運用（MVPは手動確認） | `Report.status`（PENDING/REVIEWING/RESOLVED/DISMISSED）で運営確認状況を表現し、確認・対応（ステータス変更・対応メモ記録）は6-9章の通報管理（簡易管理画面）で行う（**確定**。プロダクトオーナー確認によりMVPスコープに追加。10章参照） |
| 管理者向け機能の権限・認証（PRD5章） | 別建ての管理者認証基盤は設けず、既存のBearerトークン認証（ADR-0003）を流用し、`User.is_admin` フラグの有無をサーバー側で追加検証する方式とする（6-9章、ADR-0007）。想定利用者が少人数の運営メンバーのみというPRD方針を踏まえ、ロール・部署等の多段階権限は導入しない |
