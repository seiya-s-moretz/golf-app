## 1. システム概要（既存踏襲）

本アプリは、ゴルフプレイヤー同士のマッチング、ラウンド募集、掲示板投稿、プロフィール管理を行うコミュニティサービスである。目的は、ゴルフ仲間の発見、ラウンド参加の促進、コミュニティ形成である（既存設計書 1章を継承、変更なし）。

PRDにより、以下がMVPスコープに追加された。
- ラウンド参加承認後・マッチング申請承認後の当事者間メッセージ
- 通報・ブロックによる安全機能
- 登録時のSMS等による簡易本人確認
- 将来のエリア拡大に耐えるエリアマスタ管理

対象OS: MVPはAndroidのみ（PRD 5章に準拠、既存設計に変更なし）。

## 2. アーキテクチャ方針（既存踏襲）

- **MVVM + Container + Hilt + Clean Architecture**（既存設計書 3章を継承）
- UI とロジックを完全分離。ViewModel は UiState（不変データクラス）を `StateFlow` で公開し、Container が Screen に橋渡しする
- 依存注入は Hilt を使用
- レイヤー責務（既存踏襲）
  - `ui/` : 画面表示・ユーザー操作の受付のみ。ビジネスロジックを持たない
  - `domain/` : ビジネスモデル・リポジトリインターフェース・ユースケース（フレームワーク非依存）
  - `data/` : API通信、DTO、DTO⇔Domainモデルのマッピング、リポジトリ実装
  - `di/` : Hiltモジュール

**拡張方針**: 新機能（メッセージ／通報・ブロック／本人確認／エリアマスタ）もこのレイヤー構成・命名規則を踏襲する。新規に導入するモジュール（認証層）についても同じ4層構成に従う。

既存設計にはAPI認証・セッション管理の定義が存在しない（`ApiService.kt` にトークンの概念がない）。本人確認機能の追加に伴い、最低限の認証基盤を新設する必要がある。詳細は ADR-0003 を参照。

### 3-3. 要確認事項（画面構成）

- メッセージ一覧画面をフッターメニュー5番目のタブとして追加するか、既存4タブ構成を維持しマイページ配下の導線とするかは、UI/UX上の判断であり、PMまたはユーザーの意思決定が必要。本書ではAPI・データモデル・画面遷移は両パターンに対応可能な形で設計しているため、実装直前にDeveloperAgent着手前に決定すれば良い（設計のブロッカーにはならない）。**暫定案としてはフッターメニューへの追加（5タブ化）を推奨する**（未読件数のバッジ表示など、メッセージ機能の可視性を担保するため）。

#### RoundEvent（既存踏襲、意味論の明確化）

既存カラムに変更なし。ただし `current`（現在人数）の更新契機を明確化する。

| 項目 | 型 | 説明 |
|---|---|---|
| event_id | UUID | 募集ID |
| club_name | String | ゴルフ倶楽部名 |
| datetime | Datetime | 日時 |
| fee | Int | 費用 |
| capacity | Int | 募集人数 |
| current | Int | 現在人数（**参加申請が「承認」された時点でのみ加算。申請中は含めない**） |
| created_by | UUID | 作成者ID（主催者） |
| created_at | Datetime | 作成日 |

意味論変更の理由: PRDが「ラウンド募集参加承認後」のメッセージ開放を要求しており、これは参加に承認ステップが存在することを前提とする。既存の詳細設計書API（`POST /round-events/{id}/join`）は`current`を即時加算する実装だったが、UI文言は一貫して「参加**申請**」としており、承認ステップの存在を示唆していた。本書ではこの前提を明文化し、参加申請→承認のワークフローとして再定義する（ADR-0001参照）。

### 5-2. 新規モデル

#### AreaMaster（エリアマスタ）

| 項目 | 型 | 説明 |
|---|---|---|
| area_id | UUID | エリアID |
| prefecture | String | 都道府県（例: 埼玉県） |
| area_name | String | エリア名（例: さいたま市、川口市など市区町村単位を想定。粒度は運用側で決定） |
| display_order | Int | 選択UI上の表示順 |
| is_active | Boolean | 提供中フラグ（trueのもののみユーザーが選択可能。falseにすることで「廃止」せず履歴を保持したままエリアを非表示にできる） |
| created_at | Datetime | 作成日 |

設計意図: 初期展開エリアの具体的な市区町村は未確定（PRD 6章の要確認事項）だが、`is_active` によって「マスタには登録するが選択肢には出さない」将来エリアの先行登録が可能。エリア拡大時はレコード追加・`is_active` 更新のみで対応でき、アプリ本体の改修は不要（詳細はADR-0002）。

#### MatchRequest（マッチング申請）

おすすめユーザー画面からの「マッチング申請（いいね）」を表すエンティティ。既存設計にはUI機能としてのみ存在し、データモデルが未定義だったため新設する。

| 項目 | 型 | 説明 |
|---|---|---|
| match_request_id | UUID | 申請ID |
| from_user_id | UUID | 申請者 |
| to_user_id | UUID | 申請先 |
| status | String(enum) | PENDING / ACCEPTED / REJECTED |
| created_at | Datetime | 申請日時 |
| responded_at | Datetime? | 承認・却下日時 |

制約: `(from_user_id, to_user_id)` の組み合わせでPENDING状態は1件まで（重複申請防止）。

#### RoundJoinRequest（ラウンド参加申請）

| 項目 | 型 | 説明 |
|---|---|---|
| join_request_id | UUID | 申請ID |
| event_id | UUID | 対象ラウンド募集ID |
| user_id | UUID | 申請者 |
| status | String(enum) | PENDING / APPROVED / REJECTED |
| created_at | Datetime | 申請日時 |
| responded_at | Datetime? | 承認・却下日時 |

制約: 承認処理は `RoundEvent.capacity > RoundEvent.current` の場合のみ成立（既存バリデーションを承認タイミングに移動）。承認者は `RoundEvent.created_by` と一致するユーザーのみ。

#### Connection（メッセージ許可関係）

マッチング申請の承認、またはラウンド参加申請の承認によって自動生成される、2ユーザー間のメッセージ許可関係。メッセージのアクセス制御の起点となる。

| 項目 | 型 | 説明 |
|---|---|---|
| connection_id | UUID | ID |
| user_a_id | UUID | ユーザーA（`user_a_id < user_b_id` となるよう正規化し重複生成を防止） |
| user_b_id | UUID | ユーザーB |
| source_type | String(enum) | MATCH_REQUEST / ROUND_JOIN |
| source_id | UUID | 起点となった MatchRequest.match_request_id または RoundJoinRequest.join_request_id |
| created_at | Datetime | 作成日時（＝承認日時） |

設計意図: ラウンド募集は主催者と各参加者の間で個別にConnectionを作る（参加者同士のConnectionは自動生成しない。PRDの要求は「当該ユーザー間」であり主催者-参加者間の連絡が主目的のため。参加者同士のグループ的な連絡はPRD3-2章の「グループチャット等の高度化」に該当しPhase2以降）。同一ユーザーペアで複数回Connectionが成立しうる（例: マッチング承認後、別途ラウンドでも参加承認）が、メッセージ機能上はConnection単位でスレッドを分けず、ユーザーペア単位で1つの会話に統合する（7章UiState設計参照）。ユーザーペアに対し既にConnectionが存在する場合、新規承認イベントはConnectionを追加生成せず、メッセージ利用可否のみ維持する（重複スレッド防止）。

#### Message（メッセージ）

| 項目 | 型 | 説明 |
|---|---|---|
| message_id | UUID | メッセージID |
| user_a_id | UUID | 会話の一方（Connection正規化と同じ並び） |
| user_b_id | UUID | 会話のもう一方 |
| sender_id | UUID | 送信者（user_a_idまたはuser_b_idのいずれか） |
| content | String | 本文（最大文字数はDeveloperAgent実装時にサーバー側バリデーションとして定義。目安500文字） |
| created_at | Datetime | 送信日時 |
| read_at | Datetime? | 受信者による既読日時（未読はnull） |

備考: `(user_a_id, user_b_id)` の正規化ペアで会話をグルーピングする。会話一覧はこのペア単位で最新メッセージを集約して表示する。

#### Report（通報）

| 項目 | 型 | 説明 |
|---|---|---|
| report_id | UUID | 通報ID |
| reporter_user_id | UUID | 通報者 |
| target_type | String(enum) | USER / BOARD_POST |
| target_id | UUID | 通報対象のuser_idまたはpost_id |
| reason_category | String(enum) | SPAM / DATING_SOLICITATION（出会い目的利用）/ HARASSMENT / INAPPROPRIATE_CONTENT / OTHER |
| reason_text | String? | 自由記述（reason_category=OTHER時は必須） |
| status | String(enum) | PENDING / REVIEWED / ACTION_TAKEN / DISMISSED |
| created_at | Datetime | 通報日時 |
| reviewed_at | Datetime? | 運営確認日時 |

備考: `reason_category` に `DATING_SOLICITATION` を設けたのは、PRD 4章「恋愛・出会い目的での利用禁止」の明記方針を通報理由の選択肢として具体化するため。ステータス更新（PENDING→REVIEWED等）を行う管理画面・管理APIは本書のスコープ外（PRD5章「モデレーション運用はMVP時点で運営による手動確認」のとおり、運営側の確認手段は本アプリ外の運用（DB直接操作や別途の軽量管理ツール）を想定。管理者向けAPI・画面の要否は要確認事項とする）。

#### Block（ブロック）

| 項目 | 型 | 説明 |
|---|---|---|
| block_id | UUID | ID |
| blocker_user_id | UUID | ブロックした側 |
| blocked_user_id | UUID | ブロックされた側 |
| created_at | Datetime | ブロック日時 |

効果（サーバー側フィルタとして実装。詳細は6-8章）:
- `GET /users/recommend`: ブロック関係（双方向）にあるユーザーを結果から除外
- `GET /board`: ブロックしたユーザーの投稿を除外
- 加えて本書の設計判断として、ブロック関係にあるユーザー間の新規 `MatchRequest` 送信・`RoundJoinRequest` 送信・メッセージ送信もサーバー側で拒否する（安全機能として当然要求される挙動と判断。PRDの明記は「おすすめユーザー・掲示板への非表示」のみのため、範囲拡張について**要確認事項**とする。10章参照）
- 既に成立している `Connection` ・メッセージ履歴は削除しない（ブロック後も履歴閲覧は可能、新規送信のみ拒否。証跡保全のため）

## 6. API設計拡張

既存API（`GET /round-events`, `POST /round-events`, `GET /users/recommend`, `GET /board`, `POST /board`, `GET /users/{id}`, `PUT /users/{id}`）は原則維持する。挙動変更のあるものは明記する。

認証: 本人確認完了後に発行されるアクセストークンを `Authorization: Bearer <token>` ヘッダーで送信する前提とする（新規、ADR-0003）。以下のAPI一覧で特記のないものは全て認証必須。

### 6-1. 本人確認・認証（新規）

#### `POST /auth/phone/otp`
- 電話番号を指定しSMSでOTPを送信する
- パラメータ: `phone_number`
- 認証: 不要
- バリデーション: 同一電話番号への再送信は一定間隔（例: 60秒）を空ける

#### `POST /auth/phone/verify`
- OTPを検証する
- パラメータ: `phone_number`, `otp_code`
- 認証: 不要
- レスポンス: 検証成功時、登録画面に進むための一時トークン `registration_token`（短期有効・アカウント未作成の状態でのみ使用）

#### `POST /users`（新規登録。既存設計に存在しなかったため新設）
- プロフィール初回登録とアカウント作成を兼ねる
- パラメータ: `registration_token`, `name`, `gender`, `age`, `area_id`, `average_score`, `purpose`, `introduction`
- レスポンス: 作成された `User`、以降のAPI利用に使う `access_token`
- 認証: 不要（`registration_token` が認証代わり）

#### `POST /auth/login`
- 既存ユーザーの再ログイン（電話番号 + OTP方式を再利用）
- パラメータ: `phone_number`, `otp_code`
- レスポンス: 認証成功したユーザー本人の `User`、`access_token`（**変更**: 当初 `access_token` のみとしていたが、クライアントがログイン後すぐに「誰としてログインしたか」を把握できる必要があるため `User` を含める形に変更した。理由はADR-0005参照）
- `POST /users`（新規登録）と同一のレスポンス形（`User` + `access_token`）に統一する

### 6-2. エリアマスタ（新規）

#### `GET /areas`
- 選択可能なエリア一覧取得（`is_active=true` のみ、`display_order` 昇順）
- レスポンス: `AreaMaster[]`
- 認証: 不要（登録前の画面でも使用するため）

備考: エリアマスタの追加・編集・無効化を行う管理者向けAPI・管理画面は本書のスコープ外（10章の要確認事項）。MVPでは運営がDBを直接操作する運用を想定。

### 6-3. ユーザー・プロフィール（既存拡張）

#### `GET /users/{id}`（既存踏襲）
- レスポンスに `area`（AreaMasterの参照展開）, `phone_verified` を追加

#### `PUT /users/{id}`（既存拡張）
- パラメータに `area_id` を追加（既存の `location` 文字列パラメータを置き換え）
- バリデーション（既存踏襲）: 年齢0〜120、スコア40〜200、目的enum、`area_id` はAreaMasterに存在し `is_active=true` であること

#### `POST /users/{id}/block`（新規）
- 対象ユーザーをブロックする
- パラメータ: なし（パスの{id}が対象）

#### `DELETE /users/{id}/block`（新規）
- ブロック解除

#### `GET /users/me/blocks`（新規）
- 自分がブロックしたユーザー一覧取得

### 6-4. ラウンド募集（既存拡張：申請承認フロー化）

#### `GET /round-events`（既存踏襲）
- レスポンスからブロック関係にある作成者の募集を除外（要確認事項、10章参照）

#### `POST /round-events`（既存踏襲、変更なし）

#### `POST /round-events/{id}/join-requests`（**既存 `POST /round-events/{id}/join` を置き換え**）
- 参加申請を作成（`status=PENDING`）。この時点では `current` を加算しない
- バリデーション: `capacity > current`（申請時点の空き状況チェック。厳密な排他は承認時に再チェック）

#### `GET /round-events/{id}/join-requests`（新規）
- 主催者が自分の募集への参加申請一覧を取得（`created_by` 本人のみ許可）

#### `POST /round-events/{id}/join-requests/{requestId}/approve`（新規）
- 参加承認。`capacity > current` を再検証のうえ `current` を加算し、`RoundJoinRequest.status=APPROVED`、`Connection` を作成（主催者⇔申請者）
- 認可: `created_by` 本人のみ

#### `POST /round-events/{id}/join-requests/{requestId}/reject`（新規）
- 参加却下

### 6-5. おすすめユーザー・マッチング申請（既存拡張）

#### `GET /users/recommend`（既存踏襲）
- レスポンスからブロック関係にあるユーザーを除外（PRD明記事項）

#### `POST /users/{id}/match-requests`（**既存の「マッチング申請（いいね）」機能を明文化**）
- マッチング申請を作成（`status=PENDING`）

#### `GET /users/me/match-requests?direction=received|sent`（新規）
- 自分宛/自分発のマッチング申請一覧取得

#### `POST /match-requests/{id}/approve`（新規）
- マッチング承認。`Connection` を作成
- 認可: `to_user_id` 本人のみ

#### `POST /match-requests/{id}/reject`（新規）

### 6-6. 掲示板（既存拡張）

#### `GET /board`（既存踏襲）
- レスポンスからブロックしたユーザーの投稿を除外（PRD明記事項）

#### `POST /board`（既存踏襲、変更なし）

#### `POST /reports`（新規、通報共通API。掲示板・ユーザー両対応のため6-8にまとめて記載）

### 6-7. メッセージ（新規）

#### `GET /conversations`
- 自分が関わる会話一覧（Connectionが存在するユーザーペア単位）を取得
- レスポンス: 相手ユーザー概要、最新メッセージプレビュー、未読件数、最終更新日時（降順ソート）

#### `GET /conversations/{partnerId}/messages`
- 特定の相手とのメッセージ履歴取得（ページネーション: `before`（カーソル）, `limit`）
- 認可: 対象ユーザーペア間に `Connection` が存在しない場合は403

#### `POST /conversations/{partnerId}/messages`
- メッセージ送信
- パラメータ: `content`
- 認可: `Connection` が存在しない場合、またはブロック関係にある場合は403
- バリデーション: `content` 空文字不可、最大文字数超過不可

#### `POST /conversations/{partnerId}/read`
- 既読化（相手からの未読メッセージの `read_at` を更新）

### 6-8. 通報・ブロック（新規、まとめ）

#### `POST /reports`
- パラメータ: `target_type`(USER/BOARD_POST), `target_id`, `reason_category`, `reason_text?`
- レスポンス: 作成された `Report`（`status=PENDING`）

#### `POST /users/{id}/block` / `DELETE /users/{id}/block` / `GET /users/me/blocks`
- 6-3章に記載済み

## 8. 非機能要件への対応方針

| PRD該当項目 | 対応方針 |
|---|---|
| パフォーマンス（一覧系3秒以内目安） | 一覧系API（`/round-events`, `/users/recommend`, `/board`, `/conversations`）はページネーション対応を前提とし、初期表示は先頭ページのみ取得する。ブロックフィルタ等のサーバー側フィルタ処理はDB側インデックス（`blocker_user_id`等）で担保する。詳細なパフォーマンス要件・実測はDeveloperAgent／TesterAgentの検証対象とする |
| セキュリティ（TLS、個人情報の非開示） | 全通信TLS必須（NetworkModuleでhttps固定）。`GET /users/recommend` 等の一覧系レスポンスでは電話番号等の機微情報を含めず、必要な項目のみ返す設計とする。認証は6-1章のトークン方式 |
| プライバシー（住まいは市区町村粒度） | AreaMasterの `area_name` 粒度を市区町村相当に統一することで担保（GPS座標等は一切扱わない設計。既存設計・PRDと整合） |
| モデレーション運用（MVPは手動確認） | `Report.status` で運営確認状況を表現するのみとし、確認・対応自体は本アプリのAPI/画面範囲外（10章要確認事項） |
| 可用性（過度な冗長化は不要） | MVPでは単一リージョン・最小構成のサーバー構成を前提とし、インフラ設計（ホスティング先、DB選定等）はDeveloperAgent着手時に別途検討する（本書はモバイルアプリ側のアーキテクチャ・API仕様が主眼のため、サーバーサイド実装technology選定は本書スコープ外。10章要確認事項） |

## 10. 要確認事項（設計上の判断が必要／要件範囲を超える論点）

以下は要件定義の範囲を超える、またはPRDに明記がなく本書側で暫定判断した事項。実装着手前にPM/ユーザーへの確認を推奨する。

| # | 論点 | 本書での暫定対応 | 確認が必要な理由 |
|---|---|---|---|
| 1 | ブロックの効果範囲 | おすすめユーザー・掲示板からの非表示に加え、マッチング申請・ラウンド参加申請・メッセージ送信も拒否する設計とした（5-2 Block章） | PRD明記は「おすすめユーザー・掲示板への非表示」のみ。安全機能として自然な拡張と判断したが、範囲がPRDより広いため確認を推奨 |
| 2 | ラウンド募集一覧からのブロック対象除外 | 募集作成者がブロック対象の場合、一覧から除外する設計とした（6-4章） | 同上。PRDにラウンド募集への言及がないため範囲拡張の要確認 |
| 3 | 参加承認フローへの変更 | 既存設計の「即時参加（`current`加算）」から「申請→主催者承認」に変更した（ADR-0001） | PRDの「参加承認後」という文言が前提とするワークフローを明文化したもので、既存資料のUI文言（「参加**申請**」）とも整合するが、既存API仕様（即時加算）からの挙動変更であるため、想定通りかPM/ユーザーの確認を推奨 |
| 4 | 通報の運営対応手段 | `Report.status` のみ用意し、確認・対応（凍結等）を行う管理者向けAPI・画面は本書スコープ外とした | PRD5章「運営による手動確認」の実現手段（DB直接操作か、簡易管理画面が必要か）が未確定。必要であれば別途管理者向け設計が必要 |
| 5 | 初期展開エリアの具体的な市区町村 | AreaMasterの設計のみ行い、実データ（都道府県・市区町村名）は未投入とした | PRD6章に記載の通り、ユーザー確認待ちの事業判断事項（本書の設計はこの確定を待たずに着手可能な形にしてある） |
| 6 | サーバーサイドの実行環境・DB選定 | 本書ではAPIインターフェース仕様のみ定義し、サーバー実装技術（言語・フレームワーク・DB製品・ホスティング）は未選定 | 既存資料・PRDともにAndroidクライアント側の設計が中心で、サーバーサイド技術選定の言及がない。DeveloperAgent着手前に別途決定が必要 |
| 7 | SMS送信ベンダー・料金 | ADR-0003にて技術方式（電話番号+OTP）は決定したが、送信事業者（例: Twilio, AWS SNS等）の選定・費用試算は行っていない | ベンダー選定はコスト・運用体制に関わる事業判断を含むため、DeveloperAgent着手前にPM/ユーザーとの確認を推奨 |
| 8 | メッセージ一覧画面のナビゲーション位置（3-3章） | フッターメニュー5タブ化を暫定推奨とした | UI/UX上の意思決定であり、DeveloperAgent着手前に確定すればよい（設計のブロッカーではない） |

## 11. DeveloperAgentへの引き継ぎ状況

本書および `docs/adr/` 配下のADRにより、以下が確定している。
- 技術スタック・アーキテクチャ方針（既存踏襲）
- ディレクトリ構成（拡張版、4章）
- データモデル（5章）
- API設計（6章）
- 画面構成・UIState（3章、7章）

DeveloperAgentは、10章の要確認事項（特に#3「参加承認フローへの変更」と#6「サーバーサイド技術選定」）について着手前にPM/ユーザーへの確認を得ることを推奨するが、それ以外の設計は実装着手可能な状態である。

### 11-1. 差し戻し事項の反映（TesterAgent報告分）

TesterAgentの検証（`docs/test-plan.md` 4-1章）により、`POST /auth/login`のレスポンス定義漏れに起因する`AuthSession.userId`の空文字列フォールバック問題が発見された。ADR-0005のとおり是正した。DeveloperAgentは以下を修正すること（修正方針の詳細はADR-0005参照）。

| ファイル | 修正内容 |
|---|---|
| `app/src/main/java/com/golfmatch/app/data/mapper/AuthMapper.kt` | `AuthSessionResponseDto.toDomain()`内の`user?.userId.orEmpty()`という暗黙フォールバックを廃止。`user`が`null`の場合はサーバー側の契約違反とみなし、明示的に例外（例:`IllegalStateException`または専用の`AuthMappingException`）を投げる実装に変更する |
| `app/src/main/java/com/golfmatch/app/data/dto/AuthDto.kt` | `AuthSessionResponseDto`のKDocコメントを更新し、「`user`は`POST /users`・`POST /auth/login`のいずれの成功レスポンスでも常に含まれる（nullableなのはJSONパース上の防御的措置であり、業務上nullは異常系）」旨を明記する |
| `app/src/main/java/com/golfmatch/app/data/api/ApiService.kt` | エンドポイント定義・戻り値型（`AuthSessionResponseDto`）は変更不要。KDocコメントで`login`のレスポンスに`user`が含まれる旨を明記するのみで良い |
| `app/src/main/java/com/golfmatch/app/data/repository/impl/AuthRepositoryImpl.kt` | 変更不要（`toDomain()`が例外を投げるようになるため、呼び出し側は自然にエラーとして伝播する） |
| `app/src/main/java/com/golfmatch/app/domain/model/AuthSession.kt` | 変更不要（`userId: String`は非nullのまま維持してよい。サーバー契約により`user`が必須になったため、nullable化は不要と判断） |
| `app/src/test/java/com/golfmatch/app/data/mapper/AuthMapperTest.kt` | 既存の「ログインレスポンス相当(userなし)ではuserIdが空文字列にフォールバックする」というテストケースは、新しい期待動作（例外がスローされる）に合わせて更新が必要（TesterAgentと連携） |

サーバーサイド（Cloud Functions側の`/auth/login`実装）が`user`を返すようにする対応も必要になるが、これは技術設計書10章#6「サーバーサイド技術選定」と同様にDeveloperAgentのサーバー実装スコープであり、本書はインターフェース契約の変更のみを扱う。
