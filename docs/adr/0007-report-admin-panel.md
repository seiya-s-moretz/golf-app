# ADR-0007: 通報管理（簡易管理画面）の権限管理方式とデータモデル拡張

## ステータス
承認（2026-08-12、プロダクトオーナー確認によりMVPスコープに追加確定）

## コンテキスト
PRD（`docs/要件定義書.md` 3-1章・4章・5章）は当初、通報受付後の運営対応手段（一覧確認・対応ステータス変更）の実現方式を「DB直接操作か、簡易管理画面が必要か」未確定のまま、技術設計書10章#4の要確認事項としてArchitectAgentに引き継いでいた。

2026-08-12、プロダクトオーナーへの確認の結果、DB直接操作は運用上現実的でないと判断され、「通報管理（簡易管理画面）」がMVP必須（Must）としてPRDに正式追加された（PM側で`docs/要件定義書.md`を更新済み）。PRDは以下の方針を示している。
- 想定利用者は少人数の運営メンバーのみ
- 機能はMVPでは一覧確認とステータス変更に絞る（凍結等の実対応の自動化・高度化は将来検討）
- 権限管理はMVPでは最小限でよい（単一の管理者ロールで可、多段階権限は不要）
- 管理者アカウントの認証方式（既存ユーザー認証基盤の流用か、別建てか）はArchitectAgentの技術判断に委ねる

本ADRは、この管理者向け画面をどのように設計するか（特に権限の持たせ方、既存`Report`モデルへの変更有無）を決定する。

## 決定

### 権限管理方式: 既存Bearerトークン認証 + `User.is_admin`フラグ
- 別建ての管理者認証基盤（管理者専用ログイン画面、管理者専用トークン発行エンドポイント等）は設けない。
- `User`エンティティに`is_admin: Boolean`（デフォルト`false`）を追加する。運営メンバーのアカウントも一般ユーザーと同じ電話番号OTP認証（ADR-0003）でアカウントを作成し、その`User`レコードの`is_admin`を`true`にすることで管理者権限を得る。
- 管理者向けAPI（`GET /admin/reports`, `GET /admin/reports/{id}`, `PATCH /admin/reports/{id}/status`。技術設計書6-9章）は、既存のBearerトークンからユーザーを特定したうえで`is_admin=true`であることをサーバー側で検証する（`false`なら403）。
- `is_admin`の付与・剥奪を行うAPI・画面はMVPでは設けない。少人数の運営メンバーのみが対象であるため、運用者がDBを直接更新する運用とする（この点は既存のAreaMasterデータ投入（ADR-0002）や通報自体の凍結対応と同様、過剰なセルフサービスUIを避ける判断）。
- ロール・部署等の多段階権限モデルは導入しない（PRDの「単一の管理者ロールで可」という方針に厳密に従う）。

理由:
1. PRDが「権限管理はMVPでは最小限でよい」と明記しており、別建て認証基盤やロール体系は過剰設計になる
2. 既にADR-0003でBearerトークン認証基盤が確立しており、フラグ1個の追加で要件を満たせるため実装コストが最小
3. 運営メンバーは実在の電話番号を持つ少人数であり、OTP認証を経由すること自体が追加の防御（なりすまし抑止）になる。管理画面専用に別途IDパスワード認証等を新設するより安全側に倒せる

### 画面構成: 同一Androidアプリ内に管理者専用画面を追加（新規アプリ・別プラットフォームは作らない）
- 通報管理一覧画面（`ReportAdminListScreen`）・通報管理詳細画面（`ReportAdminDetailScreen`）を、既存のAndroidアプリ内に`ui/screen/admin/`として追加する（技術設計書4章）。
- 一般ユーザー向けのフッター5タブ（3-3章）には含めない。マイページ画面に、`User.is_admin=true`の場合のみ表示される「通報管理」メニュー項目を設け、そこを起点に遷移する（技術設計書3-4章・7-4章）。
- 別途Webベースの管理コンソールを新設する案も検討したが、少人数運営向けの最小機能（一覧・ステータス変更のみ）であれば、既存アプリ・既存認証基盤に相乗りするほうが実装・運用コストを抑えられるため不採用とした（下記代替案参照）。

### `Report`エンティティの拡張
- `status`の取り得る値を`PENDING / REVIEWED / ACTION_TAKEN / DISMISSED`から`PENDING / REVIEWING / RESOLVED / DISMISSED`に改称する。PRDの管理画面機能説明「未対応／対応中／対応済み」という利用者向け表現に、内部enum名の意味も揃えるための改称であり、状態の数・遷移の意味自体は変更しない（`REVIEWED`→`REVIEWING`、`ACTION_TAKEN`→`RESOLVED`の1対1リネーム）。
- `reviewed_at`を`handled_at`に置き換え、あわせて`handled_by_user_id`（対応した管理者）・`handling_memo`（対応メモ、任意）を新規追加する。管理画面で「誰が・いつ・どう対応したか」を最低限記録できるようにするため。
- 状態遷移の厳密なバリデーション（例: `RESOLVED`から`PENDING`への逆行を禁止する等の状態機械）は設けない。運営メンバーが少人数で誤操作時の訂正も容易であるため、複雑な遷移ルールを実装するコストに見合わないと判断した（過剰設計の回避）。
- 通報を受けたユーザーの凍結（`User.status=SUSPENDED`への変更）を管理画面から直接行うAPIは設けない。PRDが「凍結等の実処理の自動化・高度化は将来検討」と明記しているため、MVPでは管理画面は状況の記録（ステータス・メモ）に留め、実際の凍結対応は引き続き運用（DB直接操作等）でカバーする。

この変更は既存の`Report`関連設計（技術設計書5-2章、ADR-0004のConnection/メッセージ設計）と矛盾しない。`Connection`・`Message`はブロックとは独立した仕組みであり、通報ステータスの改称・項目追加はメッセージ機能側の設計に影響しない。

## 代替案（検討したが不採用）

### 案: 別建ての管理者認証基盤（管理者専用ID/パスワードログイン等）を新設する
一般ユーザーの認証（電話番号OTP）と切り離せる利点はあるが、(1) PRDが権限管理の最小化を明記している、(2) 少人数運営という規模感に対して認証システムを二重に持つ実装・運用コストが見合わない、という理由で不採用。

### 案: 独立したWeb管理コンソール（別アプリ・別リポジトリ）を新設する
ブラウザからアクセスできる利便性はあるが、(1) 本プロジェクトはモバイルアプリ開発に特化したチーム構成であり別アプリの新設は体制上のスコープ外、(2) MVPで要求される機能が「一覧確認・ステータス変更」のみと小さく、既存Androidアプリ・既存API・既存認証基盤の再利用で十分に要件を満たせる、という理由で不採用。将来、運営メンバーの増加や機能拡張（複数ロール、通報以外の管理対象の追加等）が必要になった時点で改めて検討する。

### 案: ロールベースアクセス制御（RBAC、複数の管理者ロールを持たせる）
「モデレーター」「管理者」等の複数ロールを設ける案も一時検討したが、PRDが「単一の管理者ロールで可、多段階権限は不要」と明記しており、少人数運営という実態にも合わないため不採用。単一の`is_admin: Boolean`で必要十分と判断した。

### 案: `Report.status`のenum値を変更せず（`REVIEWED`/`ACTION_TAKEN`のまま）管理画面のUI表示ラベルのみ日本語化する
実装差分は最小になるが、`ACTION_TAKEN`（対応実施済み）という名称がPRDの「凍結等の実処理はMVPでは自動化しない」という方針と紛らわしく、あたかも本APIが凍結等の実処理を伴うかのような誤解を招く。`RESOLVED`（対応完了・記録上の解決）という中立的な名称に改めることで、本管理画面が「記録・ステータス管理のみ」であるという設計意図をコード上でも明確にするため、改称を採用した。

## 影響
- `User`エンティティへの`is_admin`追加（技術設計書5-1章）
- `Report`エンティティの`status`enum値変更（`REVIEWED`→`REVIEWING`、`ACTION_TAKEN`→`RESOLVED`）、`reviewed_at`→`handled_at`置き換え、`handled_by_user_id`・`handling_memo`の追加（技術設計書5-2章）
- 新規API `GET /admin/reports`, `GET /admin/reports/{id}`, `PATCH /admin/reports/{id}/status`（技術設計書6-9章）
- 新規画面 `ReportAdminListScreen`, `ReportAdminDetailScreen`、対応するContainer/ViewModel/UiState（技術設計書3-2章・3-4章・4章・7章）
- `MyPageUiState`への`isAdmin`追加、マイページ画面への条件付きメニュー項目追加（技術設計書7-1章・7-4章）
- `ReportRepository`・`ReportDto`・`ReportMapper`への管理者向けメソッド/フィールド追加（技術設計書4章）
