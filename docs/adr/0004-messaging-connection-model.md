# ADR-0004: Connectionモデルによるメッセージアクセス制御

## ステータス
承認

## コンテキスト
PRD（`docs/要件定義書.md` 3-1章・4章）は、「マッチング申請承認後」または「ラウンド募集の参加承認後」に、該当ユーザー間で1:1メッセージのやり取りができることを新規Must要件として追加した。既存データモデル（User / RoundEvent / BoardPost）にはメッセージに関する定義が一切存在しない。

メッセージ機能を設計するにあたり、以下を満たす必要がある。
- 誰と誰が「メッセージ可能な関係」にあるかを判定できること（無関係なユーザー間の一方的なメッセージ送信を防ぐ）
- マッチング承認・ラウンド参加承認という異なる2つの起点から、同じ仕組みでメッセージ可否を判定できること
- 実装（DeveloperAgent）が過剰に複雑にならないこと（PRDの表現は「最低限の1:1メッセージ」であり、グループチャット等の高度化はPhase 2以降と明記されている）

## 決定
承認イベント（マッチング承認／ラウンド参加承認）の結果として `Connection` エンティティを自動生成する。`Connection` は2ユーザー間（`user_a_id`, `user_b_id`。ID文字列比較で正規化し重複防止）の「メッセージ可能な関係」を表す。

メッセージ送信APIは、送信対象ユーザーとの間に `Connection` が存在するかを都度チェックするゲートとして扱う。メッセージ本体（`Message`）は個々の `Connection` ではなく正規化されたユーザーペア単位（`user_a_id`, `user_b_id`）に紐づけ、同一ペアに対して複数の承認イベント（例: マッチング承認後、別のラウンドでも参加承認）が発生しても、会話スレッドは1つに統合する。

ラウンド参加承認では、主催者⇔各参加者間で個別に `Connection` を生成する。参加者同士の相互 `Connection` は生成しない（PRDの要求は「当該ユーザー間」であり、募集主催者との連絡調整が主目的と解釈。参加者間のグループ的なやり取りはPRD3-2章の「グループチャット等の高度化」に該当し、Phase 2以降の検討事項とする）。

ブロック関係が成立した場合も、既存の `Connection`・メッセージ履歴は削除しない。新規メッセージ送信のみサーバー側で拒否する（安全機能としてのブロックと、記録としての証跡保全を両立させるため）。

## 代替案（検討したが不採用）
### 案: Connectionを設けず、MatchRequest/RoundJoinRequestの承認状態を都度メッセージAPI側で直接参照する
Connectionという中間エンティティを省略し、メッセージ送信時に「承認済みのMatchRequestまたはRoundJoinRequestが存在するか」を都度クエリする案。実装は一見シンプルだが、(1) 起点の種類が増えるたびにメッセージ側の判定ロジックに分岐が増える、(2) 同一ユーザーペアが複数の起点でメッセージ可能になった場合の集約が煩雑になる、という理由で不採用とした。Connectionという1枚のテーブルに集約するほうが、メッセージ機能側の実装をシンプルに保てる。

### 案: 会話ごとに独立したConversationエンティティを都度生成する（承認イベントごとに新規スレッド）
LINEのグループのように、承認イベントごとに新しい会話スレッドを作る案。ユーザー体験として「なぜ同じ相手なのに会話が分かれているのか」が分かりにくく、「最低限の1:1メッセージ」というPRDのシンプルさの要求にも合わないため不採用。

## 影響
- 新規エンティティ `Connection`, `Message`（技術設計書5-2章）
- 新規API `GET /conversations`, `GET /conversations/{partnerId}/messages`, `POST /conversations/{partnerId}/messages`, `POST /conversations/{partnerId}/read`（技術設計書6-7章）
- マッチング承認API・ラウンド参加承認APIの実装時に、`Connection` 生成処理を組み込む必要がある（技術設計書6-4章・6-5章）
