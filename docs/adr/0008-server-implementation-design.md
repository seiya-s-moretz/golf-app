# ADR-0008: サーバー実装設計（Bearerトークン方式・SMS送信抽象化・ディレクトリ構成方針）

## ステータス
承認（2026-08-12）

## コンテキスト
10章#6・#7（技術設計書）でサーバー実行環境（TypeScript(Node.js) + Cloud Functions for Firebase）、DB（Firestore）、SMS送信ベンダー（Twilio）が確定した。これを受け、ADR-0003で「サーバーサイド技術選定と合わせてDeveloperAgent着手時に決定する」と留保していたBearerトークンの具体的な実装形式を含め、サーバー実装に必要な以下3点の設計判断を行う。

1. Bearerトークンの実装方式（JWT自己署名／Firebase Admin SDKのカスタムトークン・IDトークン検証の活用／不透明トークン＋サーバー側セッションストア、等）
2. SMS送信（Twilio）の抽象化方針（実Twilioアカウントが未用意のため）
3. サーバー側ディレクトリ構成の考え方（Androidクライアント側のClean Architectureレイヤー分割をサーバー側に持ち込むか）

前提として、Androidクライアント側の実装（`AuthSessionManager.kt`, `NetworkModule.kt`, `AuthDto.kt`）は以下の制約を既に持っている。
- `access_token`は不透明な文字列としてのみ扱われ、クライアントは中身を解釈せずそのまま`Authorization: Bearer <token>`ヘッダーに設定する
- トークンのリフレッシュ機構・明示的なログアウトAPIは6章のAPI仕様に存在しない
- `AuthSessionManager`はプロセス内メモリにのみセッションを保持し、アプリ再起動で実質的に再ログインが必要になる設計が既に確定している（コメントに明記）

これらの制約を変更する（＝6章のAPI仕様やクライアント実装に手を入れる）ことは本ADRのスコープ外であり、既存の契約の範囲内でサーバー側の実装方式のみを決定する。

## 決定

### 1. Bearerトークンの実装方式: 自己発行の不透明トークン（opaque token）＋ Firestoreセッションストア

`crypto.randomBytes(32)`で生成したランダム値をトークンとしてクライアントに返し、サーバー側では生トークンを保存せず`sha256(token)`をドキュメントIDとして`sessions`コレクション（`userId`, `createdAt`, `expiresAt`）に保存する。認証が必要な各リクエストは、Bearerトークンをハッシュ化して`sessions/{hash}`をポイントGetし、`userId`を解決したうえで`users/{userId}`を取得して`is_admin`・`status`（凍結判定）を検証する（技術設計書12-3章・12-4章）。

理由:
1. **即時失効可能性（revocability）が本サービスの要件と整合する。** 通報管理（簡易管理画面、ADR-0007）はユーザーの`status=SUSPENDED`への変更を扱う。凍結が「次のAPI呼び出しから即座に効力を持つ」ことが安全機能として重要だが、自己署名JWTは検証時にDB照会をしない（＝ステートレスである）ことが利点であると同時に、失効させたい場合は別途ブラックリストを持つ必要があり、結局ステートフルな仕組みを追加することになる。本方式は最初からセッションストアを持つため、`sessions`削除やUserドキュメントの`status`確認だけで自然に失効を扱える。実際には、認証ミドルウェアがどのみち`is_admin`判定のために`users/{userId}`を毎回読む必要があり（ADR-0007の権限方式）、その読み取りに`status`チェックを相乗りさせるだけで追加コストなく凍結の即時反映が実現できる
2. **既存のBearerトークン運用（明示的なリフレッシュ・ログアウトAPIが存在しない）と最も整合するのがこの方式である。** JWTは短命化＋リフレッシュトークンによる運用が定石だが、6章のAPI仕様にリフレッシュエンドポイントは存在せず、これを追加すること自体が「6章のAPI仕様は変更しない」という制約に抵触する。長命なJWTを発行する選択肢もあるが、その場合は前項の失効問題がより深刻になる（長期間有効なトークンほど、凍結後も使われ続けるリスクが大きい）
3. **実装コストが最小。** JWT自己署名は署名用シークレットの管理（Secret Manager等）・ライブラリ導入・クレーム設計が必要になる。Firebase Admin SDKのカスタムトークン/IDトークンを使う案（下記代替案）はクライアント側の追加実装（Firebase Auth SDKでのトークン交換）が必要になり、既存のクライアント実装（トークンをそのまま保存・送信するだけ）と矛盾する。不透明トークン＋Firestoreセッションストアは、Firestoreを既に全面的に使う本アーキテクチャにおいて追加の技術要素（署名アルゴリズム、外部トークン交換API）を持ち込まずに実現できる
4. 認証チェックのコストは1リクエストあたりFirestore読み取り2回（`sessions`・`users`）が発生するが、少人数運営・MVP規模のトラフィックでは無視できるコストであり、JWTの「検証がステートレスで速い」という利点を優先すべき規模ではないと判断する

有効期限は90日とし、明示的なリフレッシュは設けない（技術設計書12-3章）。クライアント側が元々セッションをプロセス内メモリにしか保持しないため、サーバー側の長い有効期限が実質的なセキュリティリスクを高めるわけではなく（アプリ再起動でどのみち再ログインになる）、90日という値は「長期間放置されたトークンを無効化する保険」程度の位置づけである。

### 2. SMS送信（Twilio）の抽象化: `SmsSender`インターフェース＋環境に応じた実装切り替え

`SmsSender`インターフェース（`send(phoneNumber, body): Promise<void>`）を設け、`TwilioSmsSender`（実装済みだが実アカウント確保まで未使用）と`ConsoleSmsSender`（OTPコードをログ出力するダミー実装）の2実装を用意する。Firebase Emulator Suite実行時（`FUNCTIONS_EMULATOR=true`を自動検知）はデフォルトで`ConsoleSmsSender`を選択し、明示的な環境変数`SMS_PROVIDER`でも上書きできるようにする（技術設計書12-5章）。

理由: 実Twilioアカウントが未用意という制約下で「コード完成」をゴールにするには、Twilio呼び出し部分を本物の依存として結合せず差し替え可能にする必要がある。今回はここが「複数データソースの抽象化」という具体的必要性を持つ数少ない箇所であり、下記3の方針（サーバー側では原則レイヤー抽象化を避ける）の中でも意図的な例外として扱う。

### 3. サーバー側ディレクトリ構成: 機能単位モジュール分割、Androidクライアントと同等のClean Architectureレイヤー化は持ち込まない

`functions/src/modules/<feature>/`配下に`routes.ts`（HTTPの受付・レスポンス整形）＋`service.ts`（バリデーション後のビジネスロジック＋Firestoreアクセス）の2層のみを置く。Android側の`domain`（リポジトリインターフェース・ユースケース）に相当する抽象化層は設けない（技術設計書12-1章）。

理由:
1. Android側のレイヤー分割は「UIフレームワークからの独立」「複数データソース（ネットワーク/ローカルキャッシュ）の抽象化」「テスト時のモック差し替え」という具体的な動機に基づくが、サーバー側にはこれらの動機が存在しない。データソースは最初からFirestore1つに固定されており、切り替え計画もない
2. ローカル動作確認・（将来の）自動テストはFirebase Emulator Suiteの実Firestoreに対して行う前提であり、モック差し替えのためのリポジトリインターフェースを用意する必要性が薄い。実データストアに対してテストするほうが本番との乖離を防げる
3. 少人数運営・MVP規模のプロジェクトで一貫して採用してきた「過剰設計を避ける」方針（ADR-0002, ADR-0007等）に合わせ、1エンドポイントあたりのボイラープレートを最小化する

エンドポイントの物理的な立て方は、6章のAPI仕様がクライアント側`ApiService.kt`の単一ベースURL（`.../api/`）配下の相対パス群として設計されていることに合わせ、**Express製の単一アプリケーションを1つのHTTPS関数（`api`）としてデプロイし、Express Routerで機能ごとに分割する**方式とする。エンドポイントごとに個別のCloud Functionを立てる方式は、関数数の増加によるコールドスタート・デプロイ管理の煩雑化を招き、少人数運営には見合わないため不採用とした。

## 代替案（検討したが不採用）

### Bearerトークン: JWT自己署名（ステートレス）
検証にDB照会が不要という利点はあるが、(1) 通報管理機能によるアカウント凍結を即座に反映させるには結局ブラックリスト等のステートフルな仕組みが必要になり、ステートレスという利点が実質的に失われる、(2) 署名鍵の管理（Secret Manager導入・ローテーション方針の検討）という新たな運用コストが発生する、という理由で不採用とした。将来的にトラフィックが増えFirestore読み取りコストが無視できなくなった場合に再検討する余地はある。

### Bearerトークン: Firebase Admin SDKのカスタムトークン発行＋クライアント側でのIDトークン交換
Admin SDKの`createCustomToken`でカスタムトークンを発行し、クライアントがFirebase Auth SDK（`signInWithCustomToken`）でIDトークンに交換し、それをBearerトークンとして使う案。Firebase純正の仕組みで検証（`verifyIdToken`）も枯れているという利点はあるが、(1) 現在のクライアント実装（`AuthRepositoryImpl`・`AuthSessionManager`）は`access_token`をサーバーから受け取った文字列としてそのまま保存・送信するだけであり、追加の交換ステップ（Firebase Auth SDKへのサインイン呼び出し）を挟むにはクライアント側の実装変更が必要になる、(2) FirebaseのIDトークンは有効期限が1時間と短く、クライアント標準のリフレッシュ機構（Firebase Auth SDKが自動的に行う）を使うにはクライアントがFirebase Auth SDKを認証の主体として使う必要があるが、これはADR-0003で「Firebase Phone Authへの全面移行は不採用」と既に判断した方針（クライアント側認証3画面を作り直さない）と実質的に同じコストを再度発生させる、という理由で不採用とした。

### Bearerトークン: Firebase Admin SDKのカスタムトークンをそのままBearerトークンとして使う（IDトークン交換を省略）
カスタムトークンはクライアントSDKでのサインイン専用に設計されており、サーバー側で`verifyIdToken`のような検証手段が用意されていない（カスタムトークンの検証は原則Firebase Authentication自体が行うものであり、Cloud Functions側で独自に検証しようとするとJWT自己署名案と同程度の実装コストがかかり、かつFirebaseの想定用途から外れた使い方になる）。素直にJWT自己署名にするか本ADRの採用案にするほうが妥当と判断した。

### SMS送信: 抽象化せずTwilio SDKを直接呼び出すコードを書き、アカウント確保まで実装を保留する
実装量は減るが、「今回はコード完成までがゴール」という制約に対し、Twilio SDKの呼び出しコード自体が実行時に必ず失敗する状態のまま「完成」とするのは動作確認（Emulator Suiteでのローカル確認）ができず不適切。ダミー実装を用意しインターフェースで差し替え可能にすることで、Twilio結合部分以外の全機能をEmulator Suite上で最後まで確認できる状態を維持できる。

### ディレクトリ構成: Androidと同じ`domain`/`data`層構成をサーバー側にも複製する
クライアント・サーバーで対称的な設計になり理解しやすいという見かけ上の利点はあるが、決定の理由1・2で述べたとおりサーバー側にはこの分割を要求する具体的な動機がなく、単なる形式的な対称性のために1エンドポイントあたりのファイル数・インターフェース定義が増えるだけであり、少人数運営プロジェクトの実装コストに見合わないと判断し不採用とした。

## 影響
- 新規Firestoreコレクション`sessions`（技術設計書12-2-2章）
- `functions/`ディレクトリ構成（技術設計書12-1章）、Express製単一HTTPS関数（`api`）としてのデプロイ方針
- SMS送信抽象化のための`SmsSender`インターフェース・`TwilioSmsSender`・`ConsoleSmsSender`（技術設計書12-5章）
- 認証・認可ミドルウェア（`authenticate`, `requireAdmin`）の実装方針（技術設計書12-4章）。ADR-0007が定めた「既存Bearerトークン基盤＋`is_admin`フラグ」の権限方式は、本ADRの不透明トークン方式の上にそのまま乗る
- Firestoreセキュリティルールを「全コレクション拒否」に単純化できる（技術設計書12-7章）。クライアントがFirestoreに直接アクセスしない前提（12-0章）が維持されることが条件
- サーバー実装フェーズ計画（技術設計書13章）における、`connections`モジュールのPhase1先行実装、ブロック除外フィルタのPhase3後付け改修という依存関係
