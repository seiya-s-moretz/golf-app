# ADR-0002: 住まい情報をエリアマスタ参照に変更する

## ステータス
承認

## コンテキスト
既存データモデル（`User.location`）は自由文字列型であり、レコメンドロジックも `user.location == target.location` という単純な文字列一致で実装されていた。

PRD（`docs/要件定義書.md` 3-1章）は、「エリア情報はマスタ管理し、将来の拡大に耐える設計とする」ことをMust要件として明記している。初期展開エリアは関東圏内の一部（例: 埼玉・千葉方面を想定、具体的市区町村は未確定）に限定し、将来的にエリアを拡大する運用が見込まれている。

自由文字列のままでは、以下の問題がある。
- 表記ゆれ（「さいたま市」「埼玉県さいたま市」等）によりレコメンドの一致判定が不安定になる
- 選択可能なエリアの一覧をアプリ側で制御できず、対応エリア外の値が入力される可能性がある
- エリア拡大時に、対応漏れや表記の一貫性を保証する手段がない

## 決定
`AreaMaster` エンティティを新設し、`User.location`（自由文字列）を `User.area_id`（`AreaMaster` への外部キー参照）に置き換える。

`AreaMaster` は `area_id`, `prefecture`, `area_name`, `display_order`, `is_active` を持つ。`is_active=false` のレコードは登録・編集画面の選択肢には表示しないが、マスタとしては保持できる。これにより、将来のエリア拡大は「新規エリアをマスタに追加し `is_active=true` にする」というデータ変更のみで対応でき、アプリ本体・APIの改修を要さない。

エリア選択肢の取得は `GET /areas`（認証不要、登録前でも利用可能）で提供する。

レコメンドロジック（既存: `user.location == target.location`）は `user.area_id == target.area_id` の一致判定に置き換える。加点方式・閾値（エリア一致40点等）自体はPRD・既存設計を変更しないため、ロジックの構造には影響しない。

## 代替案（不採用）
### 案: `User.location` は文字列のまま維持し、アプリ側でenum的に選択肢を制限する
マスタテーブルを設けずクライアント側の選択肢定義（ハードコード）で対応する案。実装は簡易だが、エリア追加のたびにアプリのリリースが必要になり、「将来の拡大に耐える設計」というPRD要件を満たさないため不採用。

## 影響
- `User` エンティティのカラム変更（`location: String` → `area_id: UUID`）
- 既存API `PUT /users/{id}` のパラメータ変更（`location` → `area_id`）
- 初期投入するエリアの実データ（都道府県・市区町村の具体名）は未確定（技術設計書10章#5、PRD6章の要確認事項）。本ADR・データモデル自体は実データ確定を待たずに実装着手可能
